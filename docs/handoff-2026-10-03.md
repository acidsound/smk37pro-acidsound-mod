## 1. 이번 세션의 결론 — 저장 트랙으로 전환

### 1.1 문제 제기 (사용자 관찰, 정확함)

우리가 실기에서 성공한 것은 **전부 휘발성**이다:

| 성과 | 위치 | 리셋 시 |
|---|---|---|
| PAD/건반 채널 분리 | `0x0201C5EC` 디스패처 런타임 판별 | 소멸 |
| 패드/건반 개별 음원 패치 | S1C 16슬롯 RAM `0x01C46E80..0x01C46F30` | 소멸 |

즉 *동작은 만들었지만 상태는 못 남긴다.*

### 1.2 원인 규명 (이번 세션)

영구 경로가 **없어서**가 아니다. 세 가지가 원인이었다:

1. **S1C5가 stock SAVE를 스스로 무력화했다** (§3.4)
2. **커밋/복원 루틴을 넣을 실행 공간이 없었다** (S1C5가 유일한 케이브 `0x0201E13E..0x0201E254`를 점유, 여유 2 B)
3. 그런데 **UI가 이미 트리거하는 기존 쓰기 경로가 존재한다** (§4) → 2번 블로커가 소멸

### 1.3 전환된 결론

> 영속화는 **빈 플래시 공간 찾기 문제가 아니라 기존 쓰기 경로에 우리 상태를 통과시키는 문제**다.
>
> 그리고 그 경로는 **앱 이미지 밖(스토리지 파티션)** 에 있어 브릭 위험이 구조적으로 낮다.

## 2. M08 / M09 브릭 vs 케이브 — 수치 확정

### 2.1 재현 방법

M08/M09 리빌드 앱 이미지(둘 다 **615,828 B**)를 바이트 비교했다:

```
build/M08-rebuild.bin  vs  build/M09-rebuild.bin
```

결과: **954 B / 156 런**. VA = `0x02000000 + 파일오프셋`.

### 2.2 변경 런 분해

| 정체 | VA | 크기 |
|---|---|---:|
| **코드 케이브** (wrapper + relocated pad bridge) | `0x0201DAFA..0x0201DBB0` | **162 B** |
| pad hook 분기 타겟 조정 | `0x0202345C` | 2 B |
| 디스플레이 마커 M08→M09 (UI에 보이는 1바이트) | `0x020569C0` | 1 B |
| **템플릿 tail (브릭 원인)** | `0x020958CE..0x02095EDE` | **789 B** |

검증: 162 + 2 + 1 + 789 = 954 ✓

케이브의 7개 런:

```
0x0201DAFA(1)  0x0201DB06(1)  0x0201DB0C(9)  0x0201DB16(61)
0x0201DB54(5)  0x0201DB5A(37) 0x0201DB80(48)  ->  끝 0x0201DBB0
```

### 2.3 정정 사항

- `docs/m09-brick-incident.md`는 템플릿 범위를 `0x020959EE..0x02095EDE`로 적었으나,
  **실제 변경 바이트는 `0x020958CE`부터** 시작한다(1,552 B 스팬 안에 789 B 변경).
  소거 대상 주소로는 **`0x020958CE`** 를 써야 한다.

### 2.4 핵심 결론

- 브릭(`0x020958xx`)과 케이브(`0x0201DAxx`)는 **약 480 KB 격리**되어 있다.
  → M09 실패는 케이브 때문이 **아니다**. 템플릿 tail을 데이터 저장소로 쓴 것이 원인.
- 케이브는 **M08에도 이미 있었고 M08은 살아남았다.** M09는 그 162 B를 다시 쓴 것 + 789 B를 건드린 것.

### 2.5 ⚠️ 케이브 재사용 불가 (v15 기준)

**M08 케이브 주소는 official v15에서 코드다.**

```
0x0201DB08: lb.z r2,[r11+0x10e]
0x0201DB48: sw r0,[r11+0x1a0]      <- 0x0201D878의 goto 타겟
0x0201DB52: pop {r14,r13,r12,r11,r10,...}
0x0201DB56: pop {psr,rets,reti}
0x0201DB5A: rti                     <- 인터럽트 복귀 시퀀스
```

M08(615,828 B)과 v15(617,012 B)는 다른 빌드이므로 주소를 그대로 옮길 수 없다.
**v15 자체의 gap을 새로 찾아야 한다.**

## 3. 스토리지 ABI — 확정

출처: `baselines/v15/analysis/persistence-s2/storage/report.md` (490줄, 정독 완료)

### 3.1 래퍼 ABI (정확)

```c
// 쓰기  0x02004b02
uint32_t write(const void *ram_source,  // r0
               uint32_t storage,        // r1
               uint32_t length);        // r2
// 반환: 성공 시 length, 실패/단축 시 0

// 읽기  0x02004870
uint32_t read(void *ram_destination,    // r0
              uint32_t storage,         // r1
              uint32_t length);         // r2
// 반환: 성공 시 length, 실패 시 0
```

- 내부 쓰기 프리미티브: `0x02004a7a` (래퍼가 `0x02004b0a`에서 호출)
- 내부 읽기 프리미티브: `0x020047d8` (래퍼가 `0x02004878`에서 호출)
- 상한 검사: `0x02004a7a`에서 `storage + length <= *(0x01c454b0+0x18)`
- **`return == 요청 길이`만 성공으로 취급할 것.** 공식 SAVE는 두 반환값을 **무시**한다(fail-closed 아님).

### 3.2 스토어 객체

```c
uint8_t *g = (uint8_t *)0x01c33260;   // v16에서는 0x01c332a0 (+0x40)
```

**`g`는 이전 문서들이 S1C 런타임 객체라 부르던 그 주소다.** 스토리지와 S1C가 같은 전역을 공유한다.

| 필드 | 역할 | 부트 생산자 |
|---|---|---|
| `*(g+0x160)` | **쓰기 주소 뷰** (래퍼들이 사용) | `0x02005eea`가 `0x0200464e` 호출 후 `0x02005eee`에 저장 |
| `*(g+0x164)` | **직접 읽기/매핑 포인터** (stock 로더) | `0x02005ef2` |

**두 필드는 교환 불가.**

### 3.3 스토리지 레이아웃 (닫힘: `+0x9209`)

```
+0x0000..+0x4000   packed banks, 4 * 32 * 0x80
+0x4000..+0x9180   raw records, 128 * 0xa3
+0x9180..+0x9200   per-record flag table (128 B)
+0x9200..+0x9209   selection (9 B)

index = bank*32 + preset          (0<=bank<=3, 0<=preset<=31)
read  ptr : *(g+0x164) + 0x4000 + index*0xa3
write addr: *(g+0x160) + 0x4000 + index*0xa3
```

**`+0x9209` 이후는 어떤 바이트도 이 분석에서 허용되지 않는다.**

### 3.4 ⚠️ S1C5가 stock SAVE를 무력화했다

공식 SAVE `0x02026d6c` (UI 핸들러 내부):

```
0x02026d6c  g[0x1ec] == 0 요구
0x02026d7a  r6 == 0xff 이면 데이터 쓰기 skip
0x02026da6  g+0x1a14 (0xa3 B) -> *(g+0x160)+0x4000+index*0xa3   [raw write]
0x02026dac  stock packer 0x0201e13e 호출 (packed 0x80 레코드 갱신)
0x02026dbe  g[0x129c+index] = 1
0x02026dd0  128 B flag table -> *(g+0x160)+0x9180
0x02026dd8  g[0x1ec] = 1
```

현재 S1C5의 변경:

| 사이트 | official | S1C5 | 결과 |
|---|---|---|---|
| `0x02026da6` | `beeaacee` | `04960000` | **raw write 이전(`0x02026dd4`)으로 분기** |
| `0x02026dac` | `bfeac7b9` | `00000000` | stock packer 호출 무력화 |

`0x0201e13e`는 S1C5에서 **Note Off 셀렉터 진입점**으로 재활용되어 원래 packer 본문이 사라졌다.

**따름정리:**
1. 현재 S1C5의 stock SAVE는 예약된 raw prefix를 덮어쓰지 않는다 (그래서 안전했다).
2. **stock SAVE는 커스텀 커밋 엔진으로 쓸 수 없다.**
3. **`0x02026da6`의 호출을 되돌리면 위험하다** — 그 뒤 `0x0201e13e`는 이제 무관한 셀렉터 코드다.

### 3.5 문서가 권고하는 것

1. stock raw 레코드 인덱스를 **명시적으로 예약**한다. 자유 공간이라 주장하지 말 것.
2. 각 예약 레코드의 **앞 `0x9c` 바이트만** 사용한다.
3. 155 voice 바이트 + 1 Playback Note 인코딩. 7바이트 tail은 절대 건드리지 말 것.
4. packed 레코드 / flag / selection은 그대로 둔다.
5. **17 레코드**(16 payload + 1 manifest)가 최단 fail-closed. A/B면 34.
6. 커밋은 **별도 guard된 host command**로 `0x02004b02` 호출 + 전체 길이 반환 검사 + `0x02004870` readback + CRC.
7. 복원은 **`0x02005f9c`**(stock loader 실행 **후**) 래퍼로. S1C5 상태는 마지막에 publish.
8. 128개 raw 레코드 전부 byte-identical 유지가 필수면 **이 경로는 막힌다.**

### 3.6 미증명 (문서 기준)

- 어떤 레코드도 공장 미사용/사용자 폐기가 아니다. **128개 전부 할당된 라이브러리 레코드.**
- 7바이트 raw tail도 **전부 소비자가 있다.** flag 128개와 selection 9바이트도 stock 생명주기가 있다.
- 레코드 예약 정책에 대한 제품/UI 동의 없음.
- 하위 프리미티브의 **전원 차단 원자성** 미증명.
- 쓰기 직후 **`*(g+0x164)` 일관성** 미증명 (readback 검증이 실패할 수 있음).
- **커밋/복원 루틴의 실행 위치** — S1C5가 `0x0201e13e..0x0201e254` 케이브를 점유.
- 영속화 구현의 실기 동작 — 구현/기기 동작 없음.

## 5. ⭐ 핵심 발견 — UI가 이미 트리거하는 영속 쓰기 경로

```
UI 상태머신 (0x020295c8, 후보 0x02029290 / 0x02029528 인접)
        |  call
        v
FUN_02005512  ->  call 0x02004b02  (WRITE)
        |
        v
flag table 128 B  ->  *(g+0x160) + 0x9180   [플래시 영속]
```

### 5.1 왜 중요한가

- **새 코드도, 케이브도, 커밋 루틴 실행 공간도 필요 없다.**
- 기존 UI 동작이 이미 플래시 쓰기를 수행한다.
- 대상은 **스토리지 파티션**(앱 코드 아님) → 브릭 위험이 구조적으로 낮다.
- §1.2의 2번 블로커(실행 위치)가 **소멸**한다.

### 5.2 규모

| 항목 | 크기 |
|---|---:|
| flag table | 128 B |
| 채널 분리 + 패드/건반 개별 패치 저장에 필요한 추정량 | 16슬롯 x 2 B = 32 B |

→ **128 B면 충분할 가능성이 높다.** 단 flag의 stock 의미를 침해하지 않아야 한다.

### 5.3 즉시 검증할 것 (미검증)

1. `FUN_02005512`의 flag 소스가 `g+0x129c` **고정**인가, 아니면 인자로 받는가?

→ **"정적 참조 0 + 미디코드 = 빈 공간"은 M09를 브릭시킨 바로 그 추론이다.**
→ 도구(quarkslab vs kagaimiq)가 서로 다른 구간을 놓치므로 미디코드는 빈 공간의 증거가 **아니다.**

### 6.3 도구/구현 함정 (실제로 겪음)

- `%#010x` 포맷에 VA를 두 번 더했다(`0x02000000+off`인데 `off`가 이미 VA) → 빈 hexdump가 '전부 0'처럼 보였다.
  **raw 바이트를 볼 때는 `offset = VA - 0x02000000`을 명시적으로 계산할 것.**
- JS 배열 리터럴에서 문자열이 줄바꿈으로 쪼개지면 `Expected ',', got 'string literal'`이 난다.
- `tools.write` / `tools.read`가 간헐적으로 타임아웃한다. **`bash` quoted heredoc(`<<'MDEOF'`)이 안정적이다.**
- macOS에 `timeout` / `gtimeout`이 없다.
