## Dump provenance and retention

The two archived dumps are **evidence, not a restore point**. They are a
byte-stable record of what the instrument held on 2026-10-11; they cannot be
written back. Keep them for provenance, not for rollback.

What they are: a 1 MiB raw read of the WL82 flash taken in **normal mode**, not
through the forced loader. Two independent reads are byte-identical, which
establishes that the read path is deterministic. It does not establish that the
read path sees every byte the forced loader sees.

Why a firmware package does not replace them:

- The generic official v15 `flash.bin` covers only `0x00000..0x9BFFF`
  (638,976 B). The dumps are 1 MiB. The remaining **400 KiB at
  `0x9C000..0xFFFFF` is 36.6 % non-erased and appears in no vendor package**,
  so a package restore cannot reproduce whatever lives there. Offline
  structure: `0x0A0000` is a fully erased 64 KiB gap; from `0x0C8000` to
  `0x0E7000` seven 20 KiB blocks repeat on a `0x5000` stride (three distinct
  contents, consistent with banked user data); `0x0F4000` carries a 37 KiB
  populated block. The exact ownership of these ranges is open gate 3.
- The device runs **v15**, yet 0 of the 156 sectors below `0x9C000` are
  byte-identical to the generic v15 package. Package and device are in
  different representations, so a package sector hash cannot be compared to a
  device sector at all. Blocker 2 below is measured, not assumed.
- Writing a dump back would need a validated writer and a proven
  package-to-target mapping. Neither exists, so the dumps stay read-only.

What they are good for: a pre-v16 baseline for any later "what changed"
question, and the only way to tell whether calibration and user data survived
an operation — which is exactly what a firmware package cannot tell you.

Retention decision: keep both, outside git (`/backups/` is ignored), at
`backups/smk37-pro-live-before-sloop-20261011-{a,b}.bin`, with the SHA-256
pinned above so any copy can be verified. Unlike the vendor packages they
cannot simply be re-obtained: once the device state changes, the pre-v16
content is gone.

## Blockers and strict safety gates

1. No product-specific vendor confirmation is recorded for v16-to-v15
downgrade support, accepted package/tool versions, the approved Windows
procedure, or impact on presets/calibration. Treat
`isd_download.exe -todisk FILE ADDRESS` as a Flash write and do not use it
without authoritative semantics for the exact tool.
2. The package-side `flash.bin` representation has not been mapped sector by
sector to forced-loader raw Flash. Never compare package sector hashes
straight to device hashes or write package bytes directly.
3. The extra v16 package range `0x9C000..0x9CFFF` has unresolved on-device
ownership and may intersect user/configuration data. Do not erase, overwrite,
or assume it is disposable.
4. No v16-specific target manifest, validated readback mapping, or guarded
writer exists. Existing H0/H1/H2 and other v15 rollback bundles are not
applicable.
5. The current read-only Windows tool is
[`windows-readonly/smk37_wl82_readonly.py`](../windows-readonly/smk37_wl82_readonly.py).
Its `probe` and `loader-probe` commands are read-only apart from uploading and
jumping to the hash-locked official loader in volatile RAM. Its `dump` command
is coupled to the old six-sector M09 manifest schema; **do not use that
command for a v16 target**. Do not weaken or relabel the old manifest to bypass
its checks.
   A separate `evidence-dump` command now provides the generic path: it takes
   no manifest, reuses the same read-only acquisition, and writes an
   `evidence-report.json` carrying `restore_authorized: false` and
   `physical_write_supported: false`. `--compare FILE` adds a sector-by-sector
   diff against a supplied 1 MiB image, which is what a normal-mode/forced-
   loader comparison needs. It is covered by the offline self-test on fake
   transport and has **not yet run against hardware**.
6. The app-size ceilings in `tools/check_sdk_app_layout.py`,
`sloop-smk37/tools/build_smk37.py` and
`sloop-smk37/tools/make_smk37_fwsc.py` are all the **v15** slot (617,012 B).
The v16 slot is larger (619,704 B), so the gate fails safe rather than
rejecting a valid image — but do not treat a pass of that gate as evidence
about the v16 layout. See
[the readiness assessment](v16-to-v15-recovery-readiness.md).

## Gated next steps

1. Before any separately considered v16 installation, obtain written
SMK/Jieli confirmation of downgrade support, accepted package and tool
versions, procedure, and data/calibration impact. This handoff does not
authorize installation. Recheck current device identity read-only.
2. If v16 is later installed under separate authorization and recovery becomes
necessary, enumerate Windows disks afresh and confirm exact `WL82 UBOOT1.00`.
Never reuse the hard-coded `PHYSICALDRIVE5` in the historical
[`windows-readonly/06-oneshot-consecutive.cmd`](../windows-readonly/06-oneshot-consecutive.cmd).
Use only reviewed identity/loader probes first; stop on any mismatch.
3. The generic read-only double-dump path is implemented and self-tested
(`evidence-dump`), so the remaining work is its first real run. On a healthy
v15 instrument: re-confirm identity read-only, then take two full 1-MiB
forced-loader dumps, archive their hashes and loader / device identity (device
type, device ID, Flash ID), and require byte identity. A mismatch is a hard
stop. Run `--compare` against the archived normal-mode dump at the same time:
that pairing is the only chance to establish the package/dump representation,
because a pre-install forced-loader baseline cannot be retaken once the
version changes.
4. Independently validate package-to-dump representation for every proposed
sector, including the v16-only range; decide and document preservation of the
device-specific boot prefix, JLFS structures, and user/configuration data.
5. Only after those gates, derive a new target-specific manifest and separate
allow-listed writer; test pre-hashes, exact scope, immediate readback, failure
handling, and whole-chip outside-range invariance with fake transport. Then
require human safety review and separate explicit authorization before any
physical write.
6. After any later authorized restore, verify normal USB identity `015`,
display, MIDI/audio, keys/pads, and user presets. Sector readback alone does
not prove boot or data preservation.

**Never** chip-erase, write a full-chip image, burn a key, reset the target as
part of this offline work, use arbitrary `-todisk`, write FWSC package sectors
directly, or reuse an unrelated legacy rollback bundle. This document
authorizes no physical device operation.
