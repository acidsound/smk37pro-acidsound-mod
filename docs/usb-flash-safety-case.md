## 0. 왜 이 문서가 필요한가

2026-08-15, SDK 앱을 exact_ota로 올린 뒤 쓰기 자체는 성공했지만
(`0xF0000000` ACK) 장치가 USB에 **전혀** 나타나지 않았다. 원인은 앱의 성능이
아니라 **빌드 구성**이었다: `-DCONFIG_NO_SDRAM_ENABLE`이 빠져 `.data`/`.bss`/
malloc 힙이 `0x04000000`(SDRAM 창)에 배치됐고, 이 장치의 부트 체인은 그 창을
초기화하지 않는다. 오프라인 게이트 9종은 전부 통과했다 — **링크 맵을 보는
게이트가 하나도 없었기 때문이다.**

이 문서는 그 재발을 막는 **쓰기 전 판정 절차**다.

## 1. 쓰기 경로 분류와 현재 승인 상태

| 경로 | 내용 | 현재 승인 |
|---|---|---|
| **A. 앱 전용 fwsc OTA** | 정상 모드에서 `exact_ota`로 앱 슬롯만 교체 (`0x4300..0x9A833`) | **조건부** — §2의 모든 게이트를 통과할 때만 |
| **B. 가드 섹터 복원 (파일 전용)** | `tools/smk37_guarded_restore.py`로 덤프 파일만 수정, 부트/JLFS/tail 보존 | **승인** — 장치를 건드리지 않음 |
| **C. 전체 tonorflash 쓰기** | `isd_download -uboot … -app …` — 부트 헤더(`0x0000..0x4000`)까지 기록 | **승인 불가** — 부트 영역 포맷 미확정(G-09) |
| **D. 강제 로더 쓰기** | Jieli Forced Upgrade Tool 4.0 / WL82 UBOOT1.00 로더 RAM 업로드 | **복구 전용** — 정상 쓰기 수단으로 사용 금지 |

> A 경로는 `docs/firmware-runbook.md`의 guarded restore가 다루는 경로와 같다.
> 이 문서는 그 위에 **SDK(비-SMK) 앱**을 올릴 때의 추가 게이트를 정의한다.

## 2. Pre-flight 게이트 (전부 통과해야 쓰기)

각 항목은 실패 시 **중단**이다. "아마 괜찮을 것"은 통과가 아니다.

### P1. 현재 장치 identity 확인 (read-only)

```sh
scripts/smk37-fw-direct device-info
```

- 기대: `SMK-37 Pro_015` (또는 현재 설치본의 알려진 identity).
- 실패/불일치: **중단.** 어떤 가정도 세우지 말고 §5의 G-항목을 먼저 처리한다.

### P2. 복구 자산이 "이 세션에서" 동작함을 증명

쓰기 전에 **읽기 전용**으로 강제 로더 경로를 실제로 확인한다.

- WL82 UBOOT1.00 진입 확인 + **1 MiB 덤프 A/B 취득** + 두 덤프 SHA-256 동일.
- 기존 절차/번들: `docs/m09-wl82-dump-2026-08-15.md`,
  `build/SMK37Pro-WL82-M09-rollback-v1/` (로더 + SCSI 전송 + run 스크립트).
- 실패: **중단.** 복구 수단이 검증되지 않은 상태에서 쓰지 않는다.

### P3. 롤백 대상 fwsc 고정

- 되돌아갈 **정확한** fwsc(현재 설치본)의 SHA-256과 `exact_ota` 래퍼를 준비한다.
- 그 패키지로 `check`가 PASS 하는지 오프라인으로 확인한다.

### P4. 링크 맵 게이트 (신규 — 이번 사고의 직접 방지책)

```sh
python3 tools/check_sdk_app_layout.py <sdk.map> --app <app.bin> --json <out.json>
```

- `LAYOUT GATE: PASS` 여야 한다. 하나라도 `FAIL`이면 **중단**.
- 이 게이트는 `0x04000000`(SDRAM 창) · 앱 슬롯 밖 XIP · allow-list 밖 주소를
  거부한다.
- 회귀 시험: `python3 tools/check_sdk_app_layout.py --self-test` → `SELF-TEST PASS`.
- 참고: 2026-08-15에 플래시된 바로 그 `sdk.map`을 넣으면 다음이 나온다.

  ```
  FAIL .data   0x04000000..0x04000988
       -> SDRAM window. … This is the 2026-08-15 brick.
  FAIL .bss    0x040009a0..0x04003550
  ```

### P5. 패키지 게이트 (기존)

- `exact_ota check <fwsc>` 양성 PASS + 타 버전 REJECT.
- 보호 영역 불변: 부트(`0x0..0x4000`), JLFS 헤더, tail, 패키지 밖 데이터.
- 변경 감사: 앱 데이터 + CRC 필드만.

### P6. 관측 가능성 게이트

- 플래시할 앱은 **실패 시 판별 가능한 신호**를 가져야 한다.
- 2026-08-15의 앱은 "USB 하나"였다. 그 하나가 안 뜨면 판별도 복구도 불가였다.
- 최소 요건: USB descriptor identity 변화 **또는** LCD 단색 표시 **또는** 알려진
  주기의 LED/오디오 패턴 중 하나. "아무것도 안 하는 복구 전용 앱"은 금지.

### P7. 폴백 독립성 게이트

- "앱이 부팅해서 업데이트 모드를 열어 준다"는 전제에 복원을 의존시키지 않는다.
- 앱이 USB를 못 열어도 **부트롬 레벨**(P2)로 복구 가능해야 한다.
- 이 게이트를 통과하지 못하면, 그 실험은 "복구 불가 위험을 감수"하는 것이므로
  명시적 승인 없이는 진행하지 않는다.

### P8. 전원·물리 조건

- 외부 전원 + USB-C 직결. 허브 금지.
- 녹색 LED/전원 상태를 사용자가 확인. 배터리로 돌아가는 상태에서 쓰지 않는다.
- macOS: `MIDIServer`가 인터페이스를 점유하면 claim이 `LIBUSB_ERROR_ACCESS`로
  실패한다. `scripts/run-without-midiserver`로 실행한다.

### P9. 세션 기록 준비

- transcript 경로(`logs/v15/ota-<빌드>-<타임스탬프>.log`)를 미리 정하고,
  플래시 직전 상태(identity, 덤프 SHA-256, 패키지 SHA-256)를 같은 세션에 남긴다.

## 3. In-flight 규칙

1. 플래시 중 **USB를 분리하지 않는다.**
2. stage 전환이 안 보이면 재시도로 밀어붙이지 않는다. 먼저 버스 상태를 본다.
3. 두 번째 stage가 시작되지 않으면, 그 상태 자체를 기록하고 멈춘다.
   (동일 파일 재업로드는 Jieli가 문서상 거부한다 — `0x400F`.)
4. 예상 밖 출력이 하나라도 나오면 즉시 중단하고 §6으로 간다.

## 4. Post-flight 검증

| 단계 | 기대 | 실패 시 |
|---|---|---|
| 재인넘레이션 | 알려진 identity가 5초 내 복귀 | §6 |
| identity | `SMK-37 Pro_0xx` | §6 |
| read-only dump A/B | byte-identical | 쓰기 범위 재검토 |
| 기능 회귀 | UI/건반/노브/MIDI 입출력 | 롤백(P3) |

---

## 5. 중단(ABORT) 조건 — 하나라도 해당하면 즉시 멈춘다

- P1~P9 중 하나라도 실패
- USB 버스에서 장치가 사라짐 (정상/업데이트 어느 identity도 안 뜸)
- `LIBUSB_ERROR_ACCESS`가 원인 불명으로 반복
- 사전 덤프 A/B가 서로 다름
- 롤백 패키지의 `check`가 PASS 하지 않음
- 사용자가 장치의 물리 상태(전원/LED)를 확인해 주지 못함

**중단 후 첫 행동**: 쓰기 재시도가 아니라 **읽기 전용 상태 확정**
(`device-info`, 버스 스캔, 강제 로더 진입 가능 여부)이다.

## 6. 2026-08-15 사고에서 도출된 규칙

| # | 규칙 | 이유 |
|---|---|---|
| R1 | **검증한 바이너리와 올리는 바이너리의 SHA-256이 같아야 한다.** 패키지 manifest의 `sdk_app_bin.sha256`과 빌드 산출물 `app.bin`을 직접 대조한다. | 게이트는 NO_SDRAM 빌드를 통과시켰고 실제로는 다른 빌드를 올렸다. |
| R2 | **링크 맵을 게이트로 강제한다**(P4). 문서 규칙이 아니라 실행되는 검사여야 한다. | 같은 실수는 눈으로는 안 잡힌다. |
| R3 | **확정 메모리 맵에 없는 주소를 쓰는 빌드는 거부한다.** | `0x04000000`은 확정 맵에 없었다. |
| R4 | **"복구 전용" 앱이라도 관측 가능한 출력을 가진다**(P6). | 실패 시 판별 신호가 0이면 원인 분석도 불가능하다. |
| R5 | **새 부팅 경로는 폴백을 먼저 만든다**(P7). | 자기복구 설계가 오히려 복구를 불가능하게 만들었다. |
| R6 | **부트 영역(`0x0..0x4000`)은 어떤 실험에서도 쓰지 않는다.** | 장치별 데이터이며 어떤 패키지로도 재구성되지 않는다. |

## 7. 남은 전제 (이 게이트들이 아직 닫지 못한 것)

확장 맵 §5의 G-항목 중 플래싱과 직접 연결되는 것:

- **G-01** (대부분 해소) SDK 동봉 `AC7911B8_Datasheet_V1.0.pdf` §4의 부품 번호
  규칙상 메모리 코드 `8` = 8 Mbit Flash이고 SDRAM/PSRAM은 같은 자리의 다른 코드
  (A/B/C/D)다 → 이 부품은 SDRAM 멤버가 아니다. 잔여: **외부** DRAM 다이 실장
  여부만 FCC/오너 보드 사진으로 판독하면 된다(개방 불필요).
- **G-02** SMK 부트 체인이 `0x01c7fd50..0x01c7fe00`을 쓰는가 → SDK `BOOT_INFO`/
  `UPDATA_BEG` 재사용 가능성.
- **G-03/G-04** v15의 USB 초기화·클럭/PLL 시퀀스 → SDK 앱이 USB를 띄우려면 필수.
- **G-09** `0x0..0x4000` 부트 영역 포맷 → C 경로(전체 플래시)를 승인하려면 필수.

이 중 **G-03, G-04(그리고 G-01의 잔여 외부 DRAM 확인)가 닫히기 전에는 SDK 앱을
올리는 실험을 재개하지 않는 것을 권고한다.** 그 전까지 진척 가능한 안전 트랙은 §1의 B 경로(파일 전용 분석),
정적 분석(G-05~G-08), 그리고 호스트 측 도구·에디터 작업이다.

## 8. 명시적 비주장

- 이 문서는 어떤 플래시도 승인하지 않는다. 승인은 게이트 통과 + 사용자 확인이다.
- 실기기 미접촉. 이 문서 작성 중 어떤 쓰기·OTA·리셋·덤프도 수행하지 않았다.
- P4 게이트는 **알려진** 위험 클래스(SDRAM 배치, 슬롯 초과, 미지 주소)를 막는다.
  모든 하드웨어 초기화 차이를 검출하지는 못한다(G-03/G-04가 그 부분이다).
- 기존 [firmware-runbook.md](firmware-runbook.md)를 대체하지 않는다. 그 문서는
  SMK 패키지 경로를, 이 문서는 비-SMK(SDK) 앱 경로의 추가 조건을 다룬다.
