# v15 ↔ v16 애플리케이션 diff (2026-10-01)

펌웨어 16(1.16, 2026-08-12)을 복원·복호화해서 v15와 바이트 단위로 대조한 결과다.
**둘 다 디코드된 앱 이미지를 얻었고, v15 쪽은 기존 정답 해시와 일치해 경로가 검증됐다.**

이 개정판은 **2단계(016용 디스어셈블 → 바이트 검증 함수 단위 diff)** 결과를 반영한다.
1단계(24 B 앵커 기반 이동 추정)는 부록 A로 내려갔다.

전 과정은 **오프라인 분석**이다. 실기기를 쓰지 않았고(쓰기/OTA/리셋/덤프 없음),
장치 identity도 확인하지 않았다.

## 0. 시작 전 게이트 (통과 확인)

| 게이트 | 명령 | 결과 |
|---|---|---|
| SDK/app 레이아웃 | `python3 tools/check_sdk_app_layout.py --self-test` | `SELF-TEST PASS` |
| v15 USB-flash readiness 기준선 | `cd baselines/v15/analysis/usb-flash-readiness && python3 validate.py` | `PASS rows=50 links=13 sha256=d4bab25b…` |
| v15 모드 능력표 | `python3 tools/validate_v15_mod_capabilities.py` | 공식 `36fe8299…`, R01 `e12ac71d…`, 패키지 `29280938…` (live 검증 5/6, VOICE-03 반증) |

세 게이트 모두 exit 0.

## 2. 복원 방법 (재현 가능)

`tools/smk37_fwsc_app_extract.py` — 레이아웃이 바뀐 패키지도 처리한다.

1. FWSC 메타데이터(48 B × 20 슬롯, 슬롯당 47 B) 언랩 → UFW payload
2. **flash.bin 위치를 고정값으로 가정하지 않는다.** 후보 오프셋마다 앱 영역을
   복호화해 JLFS 이름 `app_area_head`가 나오는 지점을 찾는다 →
   015는 `0x400`, 016은 `0x410`
3. JLFS 엔트리(flash `0x4000`=`app_area_head`, `0x4020`=`app.bin`)를 읽어
   앱 오프셋/크기 획득 (016은 `offset=0x120`, `size=619,704`)
4. 앱 영역 SFC 복호화: 블록 키 `= CHIP_KEY(0x980F) ^ ((addr - 0x4000) >> 2)`,
   키스트림 = LFSR(0x1021)

```sh
python3 tools/smk37_fwsc_app_extract.py build/SMK-37_Pro_016.fwsc \
  --out build/v16-analysis/app-016-decoded.bin --json build/v16-analysis/app-016.json
```

> 부수 확인: **016은 JLFS 헤더가 15바이트 이동한 것이 아니라, UFW 안에서
> flash.bin 자체가 16바이트 뒤에서 시작한다**(0x400 → 0x410). 고정 오프셋을
> 가정하면 016 앱이 전혀 나오지 않는다. 이것이 이전 시도의 실패 원인이었다.

## 3. 함수 단위 diff (확정)

### 3.1 파이프라인

1. **016용 Ghidra 리스팅 생성** — `V16DecoderAnalysis.java` + `run_v16_listing.sh`
   * Ghidra 12.1.2 headless, `pi32v2:LE:32:default`, `BinaryLoader`, base `0x02000000`
   * SLEIGH는 **quarkslab `ghidra-jieli`** (`e1bd0707…`, `pi32v2.sla` sha256 `6d774eac…`)
   * 1단계(포인터 시드 recursive)로 49,656 명령, 2단계(2 B 스윕 exhaustive)로 113,384 명령
   * 입력 이미지 SHA와 SLA SHA를 실행 전에 검증하고 `results/provenance.txt`에 기록
2. **전역 바이트 정렬** — `tools/smk37_app_diff_align.py`
   * 고유 16-mer 앵커 387,189개 → LIS로 공선 앵커 386,577개
   * 커버리지: 양쪽 각 494,142 B (v15의 80.1 %)
   * 삽입 102 B / 삭제 2 B / 치환 84,159 B / 복잡 65,760 B, 크기 차 +2,692
3. **함수 짝짓기 + 판정** — `tools/smk37_app_function_diff.py`
   * v15 함수 진입 주소를 정렬 사상으로 016 주소로 예측 → 반경 24 B 내 후보 수집
   * 후보 충돌은 **전역 품질 배정**(명령 니모닉 열 동일 여부 + 원시 바이트 일치율)으로 해소
   * 1차 배정에서 빠진 함수는 **니모닉 열 서명 전수 일치 + 바이트 일치율 ≥ 0.5**로 2차 배정
   * 판정: `relocated` / `ram_relocated` / `constants_changed` / `structural`

## 4. 우선순위 지점 정독

### 4.1 `0x0201C5EC` — Note On/Off 디스패처: **로직 무변경**

```
ram_relocated  0x0201c5ec -> 0x0201c6aa   107 -> 107 명령, 바이트 일치율 0.963
               RAM 주소 이동량: +0x88
```

107개 명령의 니모닉 열이 완전히 같고, 차이는 **RAM 주소 +0x88뿐**이다.
즉 **1.16 벤더도 이 디스패처의 분기 구조를 건드리지 않았다.**
`Local-` / `USB Rec-` 기능이 이 디스패처에 새 분기로 들어간 흔적은 없다.
우리 S1C 계보가 Ch10 분기를 넣은 자리와 같은 위치이며, 그 지점은 여전히
가장 적은 변경으로 기능을 얹을 수 있는 자리다.

### 4.2 `0x0201E13E` — S1C producer/selector: **로직 무변경, 경계·주소만 이동**

```
structural  0x0201e13e -> 0x0201e340   70 -> 105 명령, 바이트 일치율 1.000
            코드 이동 +0x202, RAM 이동 +0x40, 객체 내 오프셋 +0x24
```

바이트 일치율 **1.000** = v15 함수의 70개 명령이 016의 같은 함수 앞 70개와
**바이트 단위로 동일**하다. 016 쪽 함수는 거기서 35개 명령을 더 포함한다.

그 35개 명령은 v15 이미지에도 **바이트가 그대로 존재**하지만 v15 리스팅에서는
함수에 배정되지 않았다(경계 차이). 실제 차이는 상수뿐이다:

```
v15 0x0201E216 : mov r4,#0x1c33260 / add r5,r4,#0x3a0
v16 0x0201E418 : mov r4,#0x1c332a0 / add r5,r4,#0x3c4
```

즉 RAM 기준 +0x40, 객체 내 오프셋 +0x24 이동이다(§3.3과 일치).

> 1단계에서 이 지점에 적어 둔 "−74/+308 B 변동"은 **함수 경계 차이 + RAM 이동**이었고,
> 코드 내용 변경이 아니었다.

## 5. USB 디스크립터가 바뀌었다

디스크립터 영역 전체가 **+0xA00(2560 B)** 이동했고(앱 증가분과 별개), 내용도 변했다.

```
015 @0x02057B53 : 12 01 00 02 00 00 00 40 | 53 43 4d 4b | 00 01 | 01 02 03 01
016 @0x02058553 : 12 01 00 02 00 00 00 40 | 53 43 4b 34 | 00 01 | 00 02 03 01
                    bLength..bMaxPacket  | idVendor/idProduct | bcd | iMfr/iProd/iSer/numCfg
```

- idVendor 동일 `0x4353`, **idProduct `0x4B4D` → `0x344B`**
- iManufacturer `1` → `0` (제조사 문자열 미사용)

이 영역의 다른 디스크립터도 전부 +0xA00 이동: MIDIStreaming interface
`0x020579AE → 0x020583AE`, CIN 표 `0x02057AB0 → 0x020584B0`, 제품 문자열
`0x02057FA8 → 0x020589E6`.

**주의**: 이미지 내 디스크립터는 템플릿이고, v15에서도 이미지 값(`4353:4B4D`)과
실제 런타임 열거값(`4353:CF4D`)이 달랐다. 1.16 실기 런타임 identity는 **별도 실측**
이 필요하다. 다만 **패키지된 디스크립터가 바뀐 것은 사실**이므로, VID/PID로 장치를
거르는 우리 도구들은 1.16 장치에서 재확인이 필요하다.

## 6. UI 문자열 — 그리고 xref 부정 결과

### 6.1 블록 내용

UI 라벨 블록은 NUL로 구분된 연속 문자열 덩어리다.

| | v15 | v16 |
|---|---|---|
| 범위 | `0x0205D7BF..0x0205DB80` | `0x0205E1FF..0x0205E5C0` |
| 크기 | 961 B | 961 B |
| 문자열 수 | 143 | 137 |

016 블록을 그대로 읽으면:

```
... Algorithm-. Feedback-. Mono/Poly. Volume-. Local-. Preset-.
Key Chn-. Pad Chn-. Key Vel-. Pad Vel-. Pad Aft-. Pedal-.
Pitch Up-. Pitch Dn-. USB Rec-. #F5BC27 Firmware#. SUS.EXP.UP.DN...
```

**정정**: 1단계 문서는 `Key Chn-` / `Pad Chn-`를 신규로 적었지만, 실제로는
**v15에도 이미 있었다**(`0x0205D8A5`, `0x0205D8AE`). v16에서 `Local-`과
`USB Rec-`가 새로 들어가면서 블록이 재배열돼 주소만 이동했다.

| 문자열 | v15 | v16 | 판정 |
|---|---|---|---|
| `Key Chn-` | `0x0205D8A5` | `0x0205E2E2` | 기존 |
| `Pad Chn-` | `0x0205D8AE` | `0x0205E2EB` | 기존 |
| `Keys Channel-` | `0x0205D9E9` | `0x0205E42F` | 기존 |
| `Pads Channel-` | `0x0205D9F7` | `0x0205E43D` | 기존 |
| **`Local-`** | — | **`0x0205E2D3`** | **신규** |
| **`USB Rec-`** | — | **`0x0205E32A`** | **신규** |
| **`b9` `#9` `#11` `b13`** | — | `0x0205E215` `…18` `…1B` `…1F` | **신규** (코드 인터벌 라벨) |
| `7th` `Maj` `Min` `Dim` `Aug` `Dom` | `0x0205D80B..0x0205D836` | `0x02057B62..0x02057B79` | **UI 블록에서 빠져 문자열 풀로 이동** |

블록 내부 diff(모두 바이트 검증):

- `Local-`은 `Volume-` 뒤(`0x0205E2D3`), `USB Rec-`는 `Pitch Dn-` 뒤(`0x0205E32A`)에 삽입
- `b9` `#9` `#11` `b13`가 `Text` 뒤(`0x0205E215..0x0205E222`)에 추가
- `7th` `Maj` `Min` `Dim` `Aug` `Dom`이 UI 블록에서 빠지고 문자열 풀
  `0x02057B62..0x02057B79`로 이동했다. v16에서 `x`(0x02057B60)와 `off`(0x02057B7A)
  사이가 정확히 24 B 늘었는데, 이는 그 6개 문자열의 길이 합과 일치한다
- 결과적으로 v16 UI 블록은 143 → 137개다

> 주의: 이 961 B 블록은 순수 UI 라벨이 아니다. `sdfile_fat`, `btstack`,
> `usb_update_mode`, `(null)`, `no define getenv` 같은 **디버그/로그 문자열도
> 같은 블록에 섞여 있다.** UI 메뉴 부분은 대략 `0x0205E288..0x0205E466`이다.

`Key Chn-` / `Pad Chn-`는 키보드·패드의 채널 설정 파라미터이고, `Local-`은
그 소스에 대한 로컬 제어 차단 스위치다. **벤더의 채널 아키텍처는 이미
"소스별 채널 + 로컬 제어"로 구현되어 있다.**

### 6.2 xref — **부정 결과 (중요)**

1단계 문서 §6-2가 제안한 "문자열 xref → 파라미터 테이블" 경로는 **이 방식으로는
열리지 않는다.** 확인한 사실:

1. 이미지 전체를 훑어 라벨 문자열 시작 주소를 값으로 갖는 **절대 32비트 포인터를
   전수 조사**했다.
   * v16: 16개 히트, 해당 문자열은 `111AlB1`, `11C010`, `222D`, `A31`, `DN`,
     `Keys Channel-`, `Maj-Pen`, `Min-Pen`, `On`, `Pad Bank-`, `Step-`, `sdfile_fat`
   * **설정 메뉴 라벨(`Local-`, `USB Rec-`, `Key Chn-`, `Pad Chn-`, `Preset-`,
     `Volume-`, `Algorithm-`, `Feedback-`, `Mono/Poly`)을 가리키는 포인터는 0개**
     (v15도 동일하게 0개)
2. v16 recursive/exhaustive 리스팅 텍스트에서 해당 주소를 즉시값으로 갖는 명령 0건
   (`0x0205E2D3`, `0x0205E32A` 등 모든 표기 변형)
3. 블록 시작 주소를 가리키는 포인터도 없다

즉 라벨은 **절대 주소로 참조되지 않는다.** NUL 구분 블록을 런타임에 커서로
훑거나(인덱스 방식), 아직 디코드되지 않은 영역에서 참조하는 것으로 보인다.
(u16 오프셋 가설도 검정했지만 2바이트 값은 우연 일치가 너무 많아 판별력이 없었다.)

**따라서 "파라미터 테이블을 찾았다"고 주장하지 않는다.**
`Local-`이 어떤 상태 필드를 읽는지 확인하려면 다른 경로가 필요하다:

- `0x0205E1FF` 블록을 인덱스로 도는 메뉴 빌더 함수를 찾아 상수 인덱스를 역추적
- 문자열 대신 **신규 코드 대역**(`0x02039000..0x02041000`)을 정독
- v15 기준 UI 상태 객체(`0x01C33260`)를 1.16 기준(`0x01C332A0`)으로 옮겨
  "Local" 플래그가 추가됐는지 필드 폭 비교

## 11. 명시적 비주장 (non-claims)

- 전 과정 **오프라인 분석**이다. 실기기를 만지지 않았고, 장치 identity·런타임
  동작을 확인하지 않았다(마지막 실측 기록 2026-08-16).
- 016 패키지는 **커뮤니티 저장소에서 받은 것**이며 벤더 서명을 검증하지 않았다.
- **016 설치를 권고하지 않는다.** v15 기반 복구 자산(주소·해시·능력표)이 무효화된다.
- 함수 단위 판정은 Ghidra 함수 경계에 의존한다. 경계가 다르면 `structural`로
  보이는 쌍이 생긴다(§4.2가 그 예이며, 그때는 바이트 일치율로 판별했다).
- 정렬의 `replaced=84,159 B`는 **의미 재작성이 아니라 절대 주소·데이터 재배치**가
  대부분이다. 바이트만 보고 "8만 바이트가 바뀌었다"고 해석하면 안 된다.
- v16 exhaustive 스윕 창을 `BASE+0x58000`까지 넓혔다(v15는 `+0x57000`).
  꼬리 이동이 +0x9CA까지 있기 때문이며, 이 때문에 exhaustive 단계의
  `code_region_bytes`는 두 버전을 같은 기준으로 비교할 수 없다.
- 설정 메뉴 라벨을 참조하는 포인터/즉시값을 찾지 못했다(§6.2).
  **"파라미터 테이블을 찾았다"고 주장하지 않는다.**
