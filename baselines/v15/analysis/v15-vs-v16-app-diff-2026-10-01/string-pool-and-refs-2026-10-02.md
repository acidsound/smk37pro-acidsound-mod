# 1.15 → 1.16 문자열 풀 정밀 분석 및 참조 재조사 (2026-10-02)

> 대상: `app-015-decoded.bin` (sha256 `36fe8299…`) vs `app-016-decoded.bin` (sha256 `0f64fbf6…`)
> 방법: 이미지 직접 바이트 분석 + quarkslab recursive/exhaustive TSV 리스팅
> **하드웨어 접촉 없음(오프라인 분석 전용).**

## §0. TL;DR

1. **문자열 풀의 실제 시작 주소를 확정**했다: v15 `0x0205D7B5`, v16 `0x0205E1F5`.
   두 풀은 **정확히 +0xA40** 만큼 이동했다(풀 시작 기준 오프셋이 동일하게 유지).
2. **문자열 단위 델타를 확정**했다(양쪽 136개):
   - **추가 6개**: `b9`, `#9`, `#11`, `b13`, `Local-`, `USB Rec-`
   - **삭제 6개**: `7th`, `Maj`, `Min`, `Dim`, `Aug`, `Dom` → 풀에서 빠져 데이터 영역 `0x02057B5E` 로 **이동**(순서 동일, 내용 동일)
   - 나머지 124개 완전 동일
3. **직전 라운드 추론 정정**: `SU2`/`SU4`/`AD9` 는 **신규가 아니다** — v15에도 있었다.
4. **`b9`/`#9`/`#11`/`b13` 는 14 B 삽입**이다(`Text\0` 와 `1/4` 사이, v16 `0x0205E215..0x0205E223`).
   그런데 전역 바이트 정렬은 이 구간을 `insert` 가 아니라 **`complex`(동일 길이 교체)로 분류**했다.
   ⇒ **직전 보고의 "삽입 총계 102 B"는 하한값**이며, 문자열 풀 안의 삽입(Local- 6 B, USB Rec- 8 B 포함)은
   그 집계에 **포함되지 않았다**. (아래 §3)
5. **참조 전수 조사 결과는 여전히 전면 부정**: 합성기 메뉴 라벨 15개(`Cut Off-` … `USB Rec-`)에 대해
   - 정렬된 u32 포인터 **0개**
   - 임의 정렬 u32 포인터도 0개(`c-` 1건 제외, §4)
   - 상위 바이트 무시(별칭) 스캔 **0개**
   - 오프셋 테이블(u8/u16/u32 × 6개 베이스) **0개**
6. **`r8` 오탐 철회**: 직전 라운드에서 "문자열 풀에 `sh` 쓰기"로 보였던 `0x0200F972/978` 은
   `0x0200F93E: or r8,r5,#0x2` 로 **r8이 재할당**된 뒤의 정상 RAM 접근이었다. **플래시 쓰기 아님.**
7. **미해결 이상현상 1건 추가**: 동일 명령이 v15/v16에서 상수만 바뀌는데,
   그 상수가 **문자열을 따라가지 않고 섹션 베이스를 따라간다**(§4).

## §1. 문자열 풀 경계와 이동량

`printable/NUL` 런(run)을 기준으로 한 실제 경계:

| 항목 | v15 | v16 | 이동 |
|---|---|---|---|
| 풀 시작(문자열 런 시작) | `0x0205D7B5` | `0x0205E1F5` | **+0xA40** |
| 풀 직전 16 B | `0a00008e15920a000600001eae5d7c07` | 동일 | — |
| 첫 문자열 | `\t`, `\0\0`, `ota`, `No\n`, `data`, `bin`, ` ,.;:-_`, `Text` | 동일 | — |

직전 라운드에서 쓴 `0x0205E1FF`(=`data` 시작)는 **풀 시작이 아니라 풀 내부 주소**였다.
이 오차가 상수 오프셋 비교를 흐렸다. 이 문서의 모든 오프셋은 위 실제 시작 기준이다.

## §2. 문자열 단위 델타 (확정)

`difflib.SequenceMatcher` 로 양쪽 NUL 구분 문자열 시퀀스를 정렬한 결과:

```
equal  6 strings  ('\t' .. 'Text')
ADD    0x0205e215  'b9'
ADD    0x0205e218  '#9'
ADD    0x0205e21b  '#11'
ADD    0x0205e21f  'b13'
equal 10 strings  ('1/4' .. 'TRIAD')
DEL    0x0205d80b  '7th'
equal  3 strings  ('9Tth' .. '13th')
DEL    0x0205d81e  'Maj'
DEL    0x0205d822  'Min'
DEL    0x0205d826  'Dim'
DEL    0x0205d82a  'Aug'
equal  2 strings  ('SU2' .. 'SU4')      <-- v15에도 존재. 신규 아님
DEL    0x0205d836  'Dom'
equal 17 strings  ('AD9' .. 'Volume-')   <-- AD9도 v15에 존재
ADD    0x0205e2d3  'Local-'
equal  9 strings  ('Preset-' .. 'Pitch Dn-')
ADD    0x0205e32a  'USB Rec-'
equal 83 strings  ('#F5BC27 Firmware' .. 'H4_Controller')
```

원시 바이트 대조(값 문자열 구간):

```
v15 0x0205D7C0: ...54 65 78 74 00 | 31 2f 34 00 31 2f 34 54 00 ...   'Text\0' '1/4\0' ...
v16 0x0205E200: ...54 65 78 74 00 | 62 39 00 23 39 00 23 31 31 00 62 31 33 00 | 31 2f 34 00 ...
                                'Text\0'  'b9\0' '#9\0'  '#11\0'   'b13\0'      '1/4\0'
```

### §2.1. `7th/Maj/Min/Dim/Aug/Dom` 는 사라진 게 아니라 이동했다

v16 `0x02057B51..0x02057B79` (40 B):

```
0x02057b50 '\xff6th'      (0xff + '6th' — 앞 바이트가 0xff 라 별도 토큰)
0x02057b62 '7th'   0x02057b66 'Maj'   0x02057b6a 'Min'
0x02057b6e 'Dim'   0x02057b72 'Aug'   0x02057b76 'Dom'
0x02057b7a 'off'   0x02057b7e '-%d'    0x02057b82 '127'
```

v15 대응 구간 `0x0205718A..0x02057195` 은 **11 B** 뿐 → v16에서 이 코드 테이블이 **인라인 이름 6개를 얻었다**(+29 B).
즉 1.16은 화음 품질 이름 목록을 **문자열 풀 → 화음 데이터 테이블**로 옮겼다.

## §3. 전역 바이트 정렬의 한계 (직전 보고 정정)

`tools/smk37_structural_bytes.py` / 전역 정렬은 **k=16 앵커** 기반이다.
문자열 풀처럼 16 B 동일 앵커가 없는 구간에서는 정렬기가
`insert + shift` 대신 **`complex`(동일 길이 교체)** 를 선택한다.

실제 예 — v16 `0x0205E215..0x0205E223`:

| 분류 | 근거 |
|---|---|
| 전역 정렬 판정 | `complex` (v15 `0x0205D7D5..0x0205D7E3`, 14 B 대 14 B) |
| 실제 | **14 B 삽입** (`b9\0#9\0#11\0b13\0`), 이후 문자열 전부 +14 |

따라서 직전 보고의 **"insert_target 4블록 = 102 B, 코드영역 삽입 0 B"** 는
**앵커가 존재하는 구간에 한정된 하한**이다. 문자열 풀에서 최소 다음이 추가로 삽입되었다:

| 위치(v16) | 크기 | 내용 |
|---|---|---|
| `0x0205E215` | 14 B | `b9\0#9\0#11\0b13\0` |
| `0x0205E2D3` | 6 B | `Local-\0` |
| `0x0205E32A` | 8 B | `USB Rec-\0` |

그리고 24 B 삭제(`7th`…`Dom`, 풀 밖으로 이동). 합계로는 **+4 B 순증**.
**코드 영역 삽입은 0 B** 라는 결론 자체는 유지된다 — 추가분은 전부 데이터(문자열)다.

## §4. 참조 전수 조사 (부정 결과 + 이상현상)

### §4.1. 정렬 u32 포인터 스캔 — 0건

`Local-`/`USB Rec-`/`Cut Off-` 각 바이트 구간의 네 가지 정렬 위치 모두에서 u32 리터럴 검색 → **0건**.

### §4.2. 임의 정렬 스캔 — 1건

v16 exhaustive 리스팅에서 정렬되지 않은 위치에 `0x0205E330`(=`c-`, `USB Rec-`의 마지막 2글자)가 있었다.
정렬 기준으로 다시 읽으면 실제 명령은:

```
0x0201a78c  mov r1,#0x205e330     ; 6 B: opcode 2 B + imm32 30 e3 05 02
0x0201a792  mov r0,r4
0x0201a794  call 0x0201a6a0       ; (obj, str) - 텍스트 설정 계열
0x0201a796  pop {pc,r7,r6,r5,r4}
```

### §4.3. 별칭(상위 바이트 무시) 스캔 — 0건

`(value & 0x00FFFFFF) == (label & 0x00FFFFFF)` 조건으로 이미지 전체 u32 스캔:
`Local-`, `USB Rec-`, `Cut Off-`, 풀 시작 → **전부 0건**.
(캐시/비캐시 별칭 접근도 아니다.)

### §4.4. 미해결 이상현상 — 상수가 문자열을 따라가지 않는다

v15/v16 에서 **동일한 명령, 상수만 상이**인 지점들:

| 명령 위치(v16) | v15 상수 | v16 상수 | 풀 기준 오프셋 | 판정 |
|---|---|---|---|---|
| `0x0200EB12` | `0x0205D8E8` | `0x0205E328` | 0x133 / 0x133 | **고정** |
| `0x0200F772` | `0x0205D8DC` | `0x0205E31C` | 0x127 / 0x127 | **고정** |
| `0x0201A78E` | `0x0205D8F0` | `0x0205E330` | 0x13B / 0x13B | **고정** |
| `0x0203870C` | `0x0205DB4C` | `0x0205E592` | 0x397 / 0x39D | 문자열 추종 |
| `0x0200F75A` | `0x0205DB6C` | `0x0205E5B2` | 0x3B7 / 0x3BD | 문자열 추종 |

문자열 추종 상수(`H4_Controller`, `SHA-256` 계열)는 **문자열과 함께 이동**(+6)했다.
반면 `0x127`/`0x133`/`0x13B` 세 상수는 **섹션 베이스(+0xA40)만 따라갔다**.
그 결과 같은 상수가 v15에서는 `#F5BC27 Firmware#` 내부, v16에서는 `USB Rec-` 내부(`c-`)를 가리킨다.

**동일 오프셋이 서로 다른 문자열을 가리킨다.**

이 현상이 (a) 벤더 빌드의 스테일 오프셋인지, (b) 별도 서브섹션 기반 심볼인지,
(c) 링커 특성인지는 **미해결**이다. 현재로서는 "섹션 상대 고정 오프셋"이라는 사실만 확정한다.

### §4.5. 오탐 철회

`0x0200F972`/`0x0200F978` 의 `lh.z`/`sh r2,[r8]` 은 플래시 쓰기가 아니었다:

```
0x0200f93e  or r8,r5,#0x2      ; <-- r8 재할당
0x0200f972  lh.z r2,[r8 + 0x0]
0x0200f978  sh  r2,[r8 + 0x0]
```

r8 초기값 `0x0205E31C` 는 함수 전반에서 사용되지 않는 **dead store**
(디스패처류 함수 `FUN_0200F764`, 216 명령)였다.

## §5. 1.16 신규 데이터의 의미

### §5.1. `MinMaj` + 7바이트 테이블

v16 `0x02057DC0..0x02057DDB` (전후 포함):

```
0x02057dc0 'timer'
0x02057dc6 07 24 05 07 01 05 00        <-- 7 B (v15에도 있던 값)
0x02057dcd 'MinMaj\0'                  <-- 신규 삽입(1.16)
0x02057dd4 01 02 03 05 06 08 09        <-- 신규 삽입(1.16), 7 B
0x02057ddb 'Fader-'
```

주변 토큰은 `Fader-`, `Latch-`, `Scale-`, `Chord-`, `Octave`, `PAD %d`, `CC-100`, `Aft-%d`,
즉 **패드/컨트롤러(화음·스케일) 설정 영역**이다. 따라서 `MinMaj` 는
화음/스케일 종류 이름(Minor-Major)로, 뒤 7바이트는 그 음정 테이블일 가능성이 높다.

**단, `MinMaj`(0x02057DCD)·7바이트 테이블(0x02057DD4)·테이블 A(0x02058730)·테이블 B(0x02058E94)는
recursive/exhaustive 리스팅 어디에서도 즉치값으로 참조되지 않는다**(§4.1과 동일한 종류의 부정 결과).

### §5.2. 두 개의 신규 포인터 테이블

| 위치 | 엔트리 | 내용 |
|---|---|---|
| `0x02058730` | 6 × u32 | `#`(`…Firmware#` 끝), `AVED#`, `''`, `Step-`, `te-`, `es.bin` |
| `0x02058E94` | 13 × u32 | `ng-`, `o-`, `Pad Bank-`, `''`, `tor-`, ` Repeat-`, `Keys Channel-`, `annel-`, `s Channel-`, `Pattern`, `''`, `0x0205843C`(문자맵), `On#` |
| `0x02057DCD` | `MinMaj\0` + 7 B | §5.1 |
| `0x0205818C` | `mk4_ui_task\0` | 태스크 이름(`Arpeggiator` 옆) |

엔트리들이 문자열 **중간 주소**(접미사)를 가리키는 것은 이 툴체인의 문자열 접미사 병합 특성이다.

## §6. 디스크립터 영역 `0x02058400..0x02058F00` 구조

포인터처럼 보이는 u32를 전부 해석한 결과, 이 영역은 단일 테이블이 아니라 **혼합 디스크립터 블롭**이다:

| 구간 | 형태 |
|---|---|
| `0x02058454..0x0205847C` | NULL로 끝나는 **코드 포인터 배열** 그룹(`0x0202C3D6`, `0x0202C3EC`, 0, 0, `0x0202C30A`, …) |
| `0x02058480..0x0205849C` | 문자열 포인터 쌍(`sdfile_fat`/`le_fat`, `bc_encoder` 등) — 컴포넌트 레지스트리 성격 |
| `0x020584A0..0x020584AC` | 소형 정수(`0x00012E10`, `0x00012E14`, …) |
| `0x020584D0..0x020584FC` | **RAM 컨텍스트 포인터 테이블** — `0x01C33814/24/34/44`(stride 0x10), `0x01C33718/26/34/42`(stride 0x0E), … |
| `0x02058600..0x02058610` | 문자열 접미사 포인터(`''`, `ARA`, `''`, `in`, `dian`) — 스케일 이름 계열 |
| `0x02058A64..0x02058AA0` | 페달/커브 옵션 접미사 포인터(`#`, `S`, `''`, `DN`, `L`, `''`, `DR`, `P`, `Maj-Pen`, `Min-Pen`) |
| `0x02058B94..0x02058C0C` | 컴포넌트 이름 접미사(`ncoder`, `der`, `ncry`, `_sdfile`, `systimer`, `ate_mode`, `ma`, `er`) |

v16에서 이 영역은 다수의 `replace`/`complex` 블록으로 나타나는데,
이는 **문자열이 이동했기 때문에 포인터 값이 재배치된 결과**이며 새 엔트리 추가는 §5.2의 4곳뿐이다.

## §7. 직전 라운드 대비 정정 사항

| # | 직전 기술 | 정정 |
|---|---|---|
| 1 | `SU2`/`SU4`/`AD9` 가 1.16 신규 | **아님**. v15에도 존재 |
| 2 | 삽입 총계 = 102 B (4 블록) | **하한**. 문자열 풀에서 +28 B 삽입 / -24 B 삭제가 `complex` 로 흡수됨 |
| 3 | `0x0205E1FF` 를 풀 시작으로 사용 | 실제 풀 시작은 v15 `0x0205D7B5` / v16 `0x0205E1F5` |
| 4 | (신규) 문자열 풀에 `sh` 쓰기 의심 | **오탐**. `0x0200F93E` 에서 r8 재할당 |
| 5 | `7th`…`Dom` 이 1.16에서 제거 | **이동**. `0x02057B5E` 데이터 테이블로 옮겨짐(순서·내용 동일) |

## §8. 재현

```bash
# 문자열 풀 경계 확인
python3 - <<'PY'
from pathlib import Path
a16=Path('build/v16-analysis/app-016-decoded.bin').read_bytes()
a15=Path('build/v16-analysis/app-015-decoded.bin').read_bytes()
def run(img,a):
    o=a-0x02000000; s=o; e=o
    def pr(b): return b==0 or 32<=b<127
    while s>0 and pr(img[s-1]): s-=1
    while e<len(img) and pr(img[e]): e+=1
    return hex(0x02000000+s), hex(0x02000000+e)
print('v15', run(a15,0x0205D7BF), 'v16', run(a16,0x0205E1FF))
PY

# 문자열 단위 델타
python3 - <<'PY'
from pathlib import Path
import difflib
a16=Path('build/v16-analysis/app-016-decoded.bin').read_bytes()
a15=Path('build/v16-analysis/app-015-decoded.bin').read_bytes()
def spl(img,a,b):
    seg=img[a-0x02000000:b-0x02000000]; out=[]; cur=b''; st=0
    for i,x in enumerate(seg):
        if x==0:
            if cur: out.append((a+st,cur.decode('latin1')))
            cur=b''; st=i+1
        else:
            if not cur: st=i
            cur+=bytes([x])
    if cur: out.append((a+st,cur.decode('latin1')))
    return out
S15=spl(a15,0x0205D7B5,0x0205DB80); S16=spl(a16,0x0205E1F5,0x0205E5C0)
for tag,i1,i2,j1,j2 in difflib.SequenceMatcher(None,[s for _,s in S15],[s for _,s in S16],autojunk=False).get_opcodes():
    if tag!='equal':
        print(tag, [hex(S15[i][0])+' '+repr(S15[i][1]) for i in range(i1,i2)],
                     [hex(S16[j][0])+' '+repr(S16[j][1]) for j in range(j1,j2)])
PY

```

## §9. 비주장(non-claims)

- `Local-`/`USB Rec-` 의 **실제 구현 코드는 여전히 특정하지 못했다**. §4.2의 `mov r1,#0x205e330` 는
  v15에도 **동일 명령·다른 상수**로 존재하므로 **1.16이 새로 추가한 코드가 아니다**.
- `MinMaj` 가 화음 종류 이름이라는 것은 **주변 토큰에 근거한 추정**이며 확정이 아니다.
- §4.4의 "섹션 상대 고정 오프셋"은 **관측된 사실**이며 원인 규명은 미완이다.
  이로부터 "벤더 빌드 버그"라고 단정하지 않는다.
- `0x02058400..0x02058F00` 의 레코드 경계는 아직 확정하지 못했다.
- 설정 메뉴가 **정적 테이블 구동**이라고 단정하지 않는다.
