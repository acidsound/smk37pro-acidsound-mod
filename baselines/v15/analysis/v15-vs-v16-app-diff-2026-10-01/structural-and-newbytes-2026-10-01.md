# 016 정독: structural 12개 재검증 + 신규 바이트 전수 분석

작성 2026-10-01. 대상: `app-015-decoded.bin` (1.15) ↔ `app-016-decoded.bin` (1.16).
실기기 접촉 없음(오프라인 정적 분석만).

---

## 0. 요약 (먼저 읽을 것)

1. **1.16에는 신규 코드가 없다.** 이미지 전체에서 새로 삽입된 바이트는 **102 B**, 그마저도
   전부 데이터(문자열 1개 + 스케일 바이트 7개 + 포인터 테이블 2개)이다.
   삭제는 2 B뿐이다. 코드 영역에는 `insert` 블록이 하나도 없다.
2. **이전 보고의 "1.16 신규 코드 대역 0x02039000..0x02041000"은 정정한다.**
   그 대역의 함수들(0x02039A78, 0x0203E640, 0x0203F970, 0x02040B82 등)은
   바이트 정렬상 **신규 바이트가 0**이며, v15에 이미 있던 코드가 디컴파일러에 의해
   다른 함수 경계로 재배정된 것이다.
3. **structural 12개 중 로직 변경은 사실상 0건.**
   - 완전 바이트 동일 2건: `0x0201E13E`, `0x0203167E` (함수 경계 문제)
   - 상수/RAM 재배치만 6건
   - 재컴파일(명령 선택·레지스터 배정 변경) 3건
   - 후보 1건: `0x0201B570` — 슬롯 0-클리어 스토어 1개가 사라짐(§3.4)
4. **`Local-` / `USB Rec-`는 데이터 풀에 삽입된 문자열일 뿐**, 이를 가리키는 포인터나
   즉시값이 이미지 어디에도 없다(§6). 1.15/1.16 모두 설정 메뉴 라벨은
   절대 포인터로 참조되지 않는다.

## 2. structural 12개 — 바이트 기준 재검증

`changed base bytes`는 함수 주소 범위 안에 들어오는 정렬 블록(replace/insert/delete)의 v15측 바이트 합이다.
0이면 그 함수의 바이트는 1.16에서 완전히 동일하다.

| v15 | v16 | v15 크기 | 명령수 | 변경 바이트 | 판정 |
|---|---|---:|---:|---:|---|
| `0x02004896` | `0x02004898` | 256 B | 81→81 | 41 B (16.0%) | 상수 + 필드 오프셋 변경 |
| `0x0200676C` | `0x0200675E` | 22 B | 7→7 | 21 B (95.5%) | 필드 오프셋 0x3c→0x40 |
| `0x0200A150` | `0x0200A160` | 58 B | 18→51 | 6 B (10.3%) | RAM 재배치만 |
| `0x0200FC34` | `0x0200FC4C` | 1024 B | 350→344 | **2 B (0.20%)** | RAM + 콜 재배치만 |
| `0x0201B570` | `0x0201B59E` | 204 B | 66→66 | 41 B (20.1%) | 재컴파일 (+로직 후보 1건) |
| `0x0201E13E` | `0x0201E340` | 180 B | 70→105 | **0 B** | **바이트 동일** (경계 문제) |
| `0x020235BC` | `0x02026142` | 42 B | 16→16 | 32 B (76.2%) | 명령 선택 변경(동치) |
| `0x02028E86` | `0x02029744` | 32 B | 10→10 | 5 B (15.6%) | RAM 재배치만 |
| `0x02028EA6` | `0x02029764` | 34 B | 10→10 | 5 B (14.7%) | RAM 재배치만 |
| `0x0202E206` | `0x0202EBC4` | 108 B | 39→39 | 23 B (21.3%) | RAM 재배치만(0x1c0908c→0x1c090d0) |
| `0x0202E52A` | `0x0202EEE8` | 430 B | 141→135 | 7 B (1.6%) | 콜 대상 재배치만 |
| `0x0203167E` | `0x0203203C` | 30 B | 13→13 | **0 B** | **바이트 동일** (경계 문제) |

### 2.1 "structural"로 오판된 원인

세 가지가 섞여 있었다.

1. **함수 경계 재배정** — 같은 바이트를 디컴파일러가 다른 함수에 배정하면 명령 목록이 달라진다.
   `0x0201E13E`, `0x0203167E`, `0x0202E52A`, `0x0200FC34`가 여기 해당한다.
2. **Ghidra의 블록 주석 접두사** — `}  mov r6, r1` vs `mov r6,r1`처럼 `}`가 붙어
   mnemonic 시그니처가 어긋난다(최소 `0x02004896`).
3. **콜 대상/절대주소 재배치** — `call 0x02063260`→`0x02063c9e`, `mov r5,#0x1c33260`→`0x1c332a0`.

콜 대상 재배치 검증(정렬 맵으로 전수 확인):

| v15 콜 대상 | v16 | 정렬 맵 예측 |
|---|---|---|
| `0x02063260` | `0x02063c9e` | `0x02063c9e` ✓ |
| `0x020633fe` | `0x02063e3c` | (동일 구역 +0xA3E) ✓ |
| `0x0200424c` | `0x0200424e` | `0x0200424e` ✓ |
| `0x02048c96` | `0x02049660` | `0x02049660` ✓ |
| `0x020234a4` | `0x0202602a` | `0x0202602a` ✓ |
| `0x0201b51a` | `0x0201b548` | `0x0201b548` ✓ |

즉 **콜 그래프는 동일**하고 주소만 이동했다.

## 3. 실제로 바이트가 바뀐 4건 정독

### 3.1 `0x0200FC34` → `0x0200FC4C` (350→344, 변경 2 B)

바뀐 2 바이트는 둘 다 상수 재배치다.

- `0x0200FC3E` ⊂ `0x0200FC3C  mov r5,#0x1c33260` → `0x0200FC54  mov r5,#0x1c332a0` (RAM +0x40, 즉시값 3번째 바이트만 변화)
- `0x0200FF08` ⊂ `0x0200FF06  call 0x0200ad74` → 콜 대상 이미지 이동

**함수 크기 차이 6 명령(350→344)은 전부 함수 경계 재배정 때문이며 로직 변경이 아니다.**

### 3.2 `0x0202E52A` → `0x0202EEE8` (141→135, 변경 7 B)

바뀐 것은 `0x0202E5DA call 0x02048c96` → `0x0202EF98 call 0x02049660` **단 한 명령**이고,
정렬 맵이 정확히 그 주소를 예측한다(동일 피호출자).

정렬 diff 도구가 처음 보고한 "6개 명령 삭제"는 오탐이었다. 그 18 바이트는 두 이미지에서
**바이트 단위로 동일**하며(`a15[0x202E680:0x202E692] == a16[0x202F03E:0x202F050]`),
v16 함수의 경계 밖에 있을 뿐이다.

### 3.3 `0x02004896` → `0x02004898` (81→81, 변경 41 B)

로직(제어 흐름)은 동일하고 **상수/구조체 오프셋만** 바뀌었다.

```
- 0x0200489c  mov r9,#0x1c33260          →  0x0200489e  mov r9,#0x1c332a0     (RAM +0x40)
- 0x020048a2  add r4,r9,#0xd1c           →  0x020048a4  add r4,r9,#0xd60      (상대 +0x44)
- 0x020048a8  call 0x02063260            →  0x020048aa  call 0x02063c9e       (콜 재배치)
- 0x020048ae  lb.z r0,[r9 + 0x70e]       →  0x020048b0  lb.z r0,[r9 + 0x801] (절대 +0x133)
- 0x020048b4  sb r0,[r9 + 0x7e]          →  0x020048b6  sb r0,[r9 + 0x81]    (+3)
- 0x020048be  mov r5,#0x1c454b0          →  0x020048c0  mov r5,#0x1c45650    (RAM +0x1A0)
```

오브젝트 베이스가 +0x40 이동했는데 필드 상대 오프셋이 +4 / +0xF3 / +3으로 **불균일**하다.
즉 1.16에서 이 오브젝트의 **메모리 레이아웃이 재배치**되었다. 제어 흐름은 그대로다.

### 3.4 `0x0201B570` → `0x0201B59E` (66→66, 변경 41 B) — 유일한 로직 후보

재컴파일 흔적이 뚜렷하다.

- prologue/epilogue에서 `r13` 저장 제거(`push {rets,r13,...}` → `push {rets,...}`)
- `uextra r13,r4,0x0,0x8` → `uxtb r0,r4` (같은 연산, 다른 인코딩·레지스터)
- 루프 상수 `add r7,r10,#0x94c` → `#0x990` (+0x44), `movz r1,#0x7c8` → `#0x80c` (+0x44)
- 주소 계산 호이스팅: `sb r1,[r12 + r7]` → `add r2,r12,r10` + `sb r1,[r2 + r9]` (r9=0x990)

**차이 1건**: v15에는 `0x0201B60A  sb r9,[r13 + r7]`(r9=0)가 있고 v16에는 대응 명령이 없다.

```
v15  ifs (r6 < r1) {              v16  ifs (r6 < r1) {
       sb r9,[r13 + r7]   ;=0           sb r5,[r10 + 0xd]
       sb r5,[r10 + 0xd]                add r2,r12,r10
       sb r1,[r12 + r7]                 sb r1,[r2 + r9]    ; r2+r9 = r12+r7
     }  add r0, #0x1                  }  add r0, #0x1
```

즉 `r5-2` 슬롯을 0으로 지우는 스토어가 1.16에서 사라졌다. 나머지 두 스토어는 의미가 동일하다.

- 소스 변경일 수도, 콜 이후라 컴파일러가 제거했을 수도 있다.
- **확정하려면 실기기 런타임 확인이 필요하다(이번 세션 범위 밖, §5 하드 게이트).**
- 참고로 v16에서 `r9`는 0이 아니라 0x990(오프셋 상수)로 재활용되므로 "0 저장" 기능 자체가
  레지스터 배정에서 밀려난 것은 확실하다.

### 3.5 `0x020235BC` → `0x02026142` (16→16) — 동치 변환

```
- 0x020235C6  and r4,r0,#0xffffff7f   →  0x0202614C  bitclr r0,0x7
- 0x020235CA  sb r4,[sp+0x2]         →  0x0202614E  sb r0,[sp+0x2]
- 0x020235CE  mov r0,#0x7f           →  0x02026152  mov r4,#0x7f
- 0x020235D2  mov r0,r1              →  0x02026156  mov r4,r1
```

Pi32v2의 `bitclr Rd,#uimm5`는 **비트 번호**를 받으므로 `bitclr r0,0x7` = `r0 & ~0x80` =
`and r4,r0,#0xffffff7f`와 같다. 나머지는 r0↔r4 레지스터 교환. **의미 변화 없음.**

### 3.6 `0x0200676C` → `0x0200675E` (7→7)

```
- 0x02006772  add r2,r0,#0x3c        →  0x02006764  ldw r1,r0,#0x40
- 0x02006776  _lw r1,[r0 + 0x3c]     →  0x02006768  add r2,r0,#0x40
   if (r1 != r2) ...
```

연결 리스트의 "빈 리스트" 판정(노드 값 == 헤드 주소)이며 **오프셋만 0x3c→0x40 (+4)**.

## 4. 신규 바이트 전수 — 1.16이 실제로 추가한 것

전체 이미지의 정렬 블록 중 `insert_target`은 **4개, 합계 102 B**가 전부다.

| 위치 | 크기 | 내용 |
|---|---:|---|
| `0x02057DCD` | 14 B | `"MinMaj\0"` + `01 02 03 05 06 08 09` |
| `0x0205818C` | 12 B | `"mk4_ui_task\0"` |
| `0x02058730` | 24 B | u32 포인터 6개 (테이블 A) |
| `0x02058E94` | 52 B | u32 포인터 13개 (테이블 B) |

### 4.1 `0x02057DCD` — 스케일/인터벌 테이블

v15 문맥: `... "timer"\0 <07 24 05 07 01 05 00> "Fader-" ...`
v16 문맥: `... "timer"\0 <07 24 05 07 01 05 00> "MinMaj"\0 <01 02 03 05 06 08 09> "Fader-" ...`

- 기존 7 바이트 블롭 바로 뒤에 **같은 크기(7 B)의 새 테이블**이 삽입되었다.
- `MinMaj`는 새 음계/코드 종류 이름으로 보인다(1.15의 `7th/Maj/Min/Dim/Aug/Dom`가
  `0x0205D80B`에서 `0x02057B62`로 이동한 것과 같은 구역).
- 값 7개(01 02 03 05 06 08 09)는 반음 간격 테이블 형태다.

### 4.2 `0x0205818C` — `mk4_ui_task`

v15: `... \x90 H "Arpeggiator" ...` / v16: `... \x90 H "mk4_ui_task"\0 "Arpeggiator" ...`

- 태스크/모듈 이름 풀에 **UI 태스크 이름 1개**가 추가되었다.
- 1.16이 UI용 태스크를 하나 더 등록한다는 뜻으로 읽힌다.

### 4.3 `0x02058730` 테이블 A (6 엔트리)

| # | 값 | 문자열(접미사 병합) |
|---:|---|---|
| 0 | `0x0205E3CC` | `#` |
| 1 | `0x0205E3D7` | `AVED#` |
| 2 | `0x0205E3E1` | `` (빈 문자열) |
| 3 | `0x0205E3EB` | `Step-` |
| 4 | `0x0205E3F3` | `te-` |
| 5 | `0x02057F25` | `es.bin` (`0x02057F1D "es.bin"` 구역) |

### 4.4 `0x02058E94` 테이블 B (13 엔트리)

| # | 값 | 문자열(접미사 병합) |
|---:|---|---|
| 0 | `0x0205E3FA` | `ng-` (= `Swing-`의 꼬리) |
| 1 | `0x0205E402` | `o-` (= `Tempo-`의 꼬리) |
| 2 | `0x0205E40B` | `Pad Bank-` |
| 3 | `0x0205E414` | `` |
| 4 | `0x0205E41D` | `tor-` (= `Arpeggiator-`의 꼬리) |
| 5 | `0x0205E426` | ` Repeat-` |
| 6 | `0x0205E42F` | `Keys Channel-` |
| 7 | `0x0205E436` | `annel-` |
| 8 | `0x0205E440` | `s Channel-` |
| 9 | `0x02058330` | `Pattern` (블록 밖) |
| 10 | `0x0205E44A` | `` |
| 11 | `0x0205843C` | 문자 맵 테이블(블록 밖) |
| 12 | `0x0205E453` | `On#` |

테이블 B는 **시퀀서/아르페지에이터 설정 페이지의 항목 문자열 포인터 배열**로 보인다.
`Swing-`, `Tempo-`, `Pad Bank-`, `Arpeggiator-`, `Note Repeat-`, `Keys Channel-`,
`Pads Channel-`, `#F5BC27 On#`가 순서대로 나온다.

> **접미사 병합 주의**: 이 펌웨어의 문자열 풀은 링커가 동일 접미사를 병합한다.
> 그래서 포인터가 `Step-`의 중간(`te-`), `Swing-`의 중간(`ng-`)을 가리킨다.
이것은 정상이며, 라벨 전체가 참조되지 않았다고 단정하면 안 되는 이유다.

## 5. 문자열 풀 변경 (`Local-`, `USB Rec-`)

| | v15 | v16 |
|---|---|---|
| 풀 범위 | `0x0205D7BF..0x0205DB80` (961 B) | `0x0205E1FF..0x0205E5C0` (961 B) |
| 풀 이동 | — | **+0xA40** |

v16에서 풀에 삽입/추가된 항목:

- `b9` `#9` `#11` `b13` @ `0x0205E215..` (13 B 삽입, `Text` 뒤)
- `SU2` `SU4` `AD9` @ `0x0205E268..` (7 B 구역)
- **`Local-` @ `0x0205E2D3`** (`Volume-` 뒤, 5 B 삽입)
- **`USB Rec-` @ `0x0205E32A`** (`Pitch Dn-` 뒤, 7 B 삽입)

풀에서 빠진 항목: `7th` `Maj` `Min` `Dim` `Aug` `Dom`(24 B) → `0x02057B62..0x02057B79`로 이동.

정정 유지: `Key Chn-`(`0x0205E2E2`) / `Pad Chn-`(`0x0205E2EB`)는 **1.15에도 있었다**
(`0x0205D8A5` / `0x0205D8AE`).

메뉴 순서 == 풀 저장 순서이므로, `Local-`은 `Volume-`/`Preset-` 사이, `USB Rec-`는
`Pitch Dn-` 뒤(= 마지막) 메뉴 항목에 대응한다.

## 6. `Local-` / `USB Rec-` 참조 검색 — 부정 결과

시도한 모든 경로가 실패했다.

| 검색 | 결과 |
|---|---|
| 이미지 전체 u32 == 라벨 시작 (정렬/비정렬 무관) | `Local-` 0건, `USB Rec-` 0건 |
| u32 ∈ 새로 삽입된 문자열 바이트 범위 | `Local-` 0건, `USB Rec-` 0건 |
| recursive 리스팅 즉시값 ∈ 풀 범위 | 8건이나 전부 다른 문자열 |
| exhaustive 리스팅 즉시값 ∈ 풀 범위 | 15건(추가분은 문자열을 향한 오분기 2건) |
| 풀 기준 오프셋 테이블(u16/u32/u8, 기저 6종) | 0건 |
| 4-정렬 u32 → 라벨 시작 | 134개 중 12개만 참조, 메뉴 라벨은 `Step-`,`Pad Bank-`,`Keys Channel-` 뿐 |

전체 이미지에서 메뉴 라벨을 참조하는 즉시값은 다음뿐이다.

```
0x0200EB10  mov r14,#0x205E328   -> "Pitch Dn-" 영역의 "-"
0x0200F770  mov r8,#0x205E31C    -> "Pitch Up-" 영역의 "Up-"
0x0201125A  mov r1,#0x205E324    -> "Pitch Dn-" 영역의 "h Dn-"
0x0201A78C  mov r1,#0x205E330    -> "USB Rec-" 영역의 "c-"   <-- 유일한 인접 참조
```

`0x0201A78C`의 `c-`는 접미사 병합상 `USB Rec-`의 꼬리와 동일한 바이트를 가리킨다.
그러나 이 주소는 v16의 **exhaustive 리스팅에만** 나타나고 recursive 리스팅에서는
함수에 배정되지 않았으므로, 코드인지 데이터인지 확정하지 못했다.

### 6.1 해석과 한계

설정 메뉴 라벨(`Cut Off-`, `Volume-`, `Local-`, `Preset-`, ...)은 **절대 포인터로 참조되지 않는다.**
1.15도 마찬가지다. 따라서 다음 중 하나다.

1. 메뉴 엔진이 풀을 **순차 스캔**한다(순서 == 메뉴 순서인 것이 정황 증거).
2. 라벨은 런타임에 계산되는 주소로 접근된다(예: 풀 기준 고정 오프셋).

2번을 뒷받침하는 관찰: `Pitch` 계열 두 참조의 **풀 기준 오프셋이 1.15/1.16에서 동일**하다
(`0x11D`, `0x129`). 즉 이 상수들은 문자열 심볼이 아니라 풀 기준 고정 오프셋처럼 움직였다.
같은 함수에서 `H4_Controller`/`SHA-256` 참조는 문자열 시작을 정확히 따라가므로 혼재한다.
**이 메커니즘은 확정하지 못했다.**

> **주장하지 않는 것**: "설정 파라미터 테이블을 찾았다"고 말하지 않는다. 찾지 못했다.
> `Local-`/`USB Rec-`의 핸들러 코드도 특정하지 못했다. 코드가 없다는 뜻이 아니라,
> 정적 참조가 발견되지 않았다는 뜻이다.

## 7. 1.16 기능 변화에 대한 결론

이번 분석으로 확정할 수 있는 것:

1. **엔진은 그대로다.** Note On/Off 디스패처(`0x0201C5EC`→`0x0201C6AA`)와
   S1C 프로듀서(`0x0201E13E`→`0x0201E340`)는 바이트 동일/명령 동일하고 상수만 이동했다.
2. **추가된 것은 데이터뿐이다.** 스케일 테이블 1개, UI 태스크 이름 1개,
   시퀀서/아르페지에이터 메뉴 포인터 테이블 2개, 문자열 6개.
3. `Local-`/`USB Rec-`는 **표시 문자열 추가**이며, 대응 로직은 기존 제네릭 경로로 흡수된 것으로 보인다.
   (새 파라미터가 기존 옵션 엔진에 데이터로 등록되는 형태)
4. 따라서 1.15 기반 복구 자산 재사용 시 위험은 대부분 **RAM/데이터 오프셋**이지 코드가 아니다.
