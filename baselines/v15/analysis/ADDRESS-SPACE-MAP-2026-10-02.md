### §4.3 미지

- `0x02058314..0x0205D7B5` (v15) — USB 테이블 끝과 문자열 풀 시작 사이. 성격 미확정
- `0x0205E5C0..0x02096A34` (v16 기준) — 문자열 풀 이후 앱 끝까지
- 설정 메뉴 라벨(`Local-`, `USB Rec-`, `Volume-` 등)의 **참조 메커니즘**. 절대 포인터·임의 정렬·
  별칭(상위 바이트 무시)·오프셋 테이블 **전부 0건**
- `0x0201A78C`의 `mov r1,#0x205e330`(`c-`)이 무엇을 하는지 — v15에도 동일 명령이 있어 신규 코드는 아님

  서로 다른 문자열을 가리키는 현상의 원인

### §4.4 커버리지 한계 — 정량 (신규)

우리 recursive/exhaustive 리스팅은 **스윕 창 `BASE+0x58000`에서 끝난다.**

| 리스팅 | 행 수 | 주소 범위 |
|---|---:|---|
| v15 quarkslab recursive | 51,089 | `0x02000000..0x02056D14` |
| v15 quarkslab exhaustive | 112,211 | `0x02000000..0x02056FFE` |
| v15 kagaimiq exhaustive | 91,248 | `0x02000000..0x02056FFE` |
| v16 recursive | 49,656 | `0x02000000..0x02057F94` |
| v16 exhaustive | 113,384 | `0x02000000..0x02057FF0` |

=> v16 기준 **약 360 KiB / 619,704 B = 58.2 %** 만 덮는다.
`0x02060E2C`(allocator) 같은 알려진 코드가 **우리 창 밖**에 있다.
**우리 맵에 없다는 것을 존재하지 않는다는 뜻으로 읽으면 안 된다.**


## §5. RAM0 `0x01C00000` — v16 이동은 균일하지 않다

### §5.1 확정 / 거의 확정

| 범위 (v15) | 등급 | 소유/역할 |
|---|---|---|
| `0x01C00000..0x01C099D4` | 확정 | 초기화 데이터 RAM (부트 데이터 복사 목적지) |
| `0x01C099D4..0x01C4651C` | 확정/차단 | BSS/heap 제로 span — **제로화는 소유권이 아님** |
| `0x01C33260` -> v16 `0x01C332A0` | 확정 | S1C 런타임 객체 |
| `0x01C34C74` -> v16 `0x01C34CFC` | 확정 | 현재 스냅샷 (0x9C 바이트 페이로드) |
| `0x01C37FD0` | 거의 확정 | SysEx 스테이징 (0x9C + F7) |
| `0x01C46E80..0x01C46F30` | 확정 [live] | S1C5 소유 16슬롯 RAM + Playback Note 맵 |
| `0x01C3A2D4..0x01C3C5D4` | 거의 확정 | 부트 스택 초기값 범위 |
| `0x01C4651C..0x01C7FD50` | 미지/BLOCKED | 소유·별칭 미증명 (230 KiB) |
| `0x01C7FD50..0x01C7FD80` / `0x01C7FD80..0x01C7FE00` | 미지/BLOCKED [SDK] | BOOT_INFO 슬롯 / UPDATA 갱신 플래그 |

### §5.2 정정: RAM +0x40은 단일 상수가 아니다 (신규)

`mov`/`movz` 즉치 중 `0x01C00000..0x01C80000` 87개(v15) / 91개(v16)를 비교해
`+0x00..+0x100` 범위에서 **유일하게** 대응하는 23쌍을 얻었다:

| v15 | v16 | 증분 |
|---|---|---|
| `0x01C00000` | `0x01C00000` | +0 |
| `0x01C07ABC` | `0x01C07AFC` | +0x40 |
| `0x01C08C40` / `0x01C092CC` / `0x01C099D4` | `0x01C08C84` / `0x01C09310` / `0x01C09A18` | +0x44 |
| `0x01C0DC7C` / `0x01C0DE20` | `0x01C0DCBC` / `0x01C0DE60` | +0x40 |
| `0x01C32F78` | `0x01C32FB8` | +0x40 |
| `0x01C33903` | `0x01C33967` | +0x64 |
| `0x01C33B14` .. `0x01C34888` (9개) | — | +0x84 |
| `0x01C34AA0` / `0x01C34C74` | `0x01C34B28` / `0x01C34CFC` | +0x88 |
| `0x01C7FE00` | `0x01C7FE00` | +0 |

추가로 코드에서 직접 확인된 쌍: `0x01C33260 -> 0x01C332A0` (+0x40), `0x01C0908C -> 0x01C090D0` (+0x44).

**결론**: v16은 RAM에서 **여러 지점에 걸쳐 객체를 키웠고**, 증분은 `+0x40 / +0x44 / +0x64 / +0x84 / +0x88`로
주소에 따라 다르다. v15 기준 RAM 주소를 +0x40으로 일괄 변환하면 **상위 객체에서 어긋난다.**
(예: 스냅샷 `0x01C34C74`의 v16 주소는 `0x01C34CFC`로 **+0x88**이다.)

미확정: 각 증분이 **정확히 어느 주소에서 시작하는지**, 그리고 1.16에서 어떤 객체가 커졌는지.


## §6. SDRAM / 캐시 / MMIO — 실사용 실증 (신규)

기존 맵에서 MMIO는 '근거 있는 범위 없음'으로 비어 있었다.
`mov`/`movz` 즉치만 집계하고 비트마스크(`and`/`or`)를 배제한 결과:

| 창 | 공개 SDK 정의 [SDK] | v15 | v16 | 관측 예 |
|---|---|---:|---:|---|
| `0x00010000` lsfr | USB `0x18`, USB2 `0x27`, audio `0x2f`, ADC `0x31`, EQ `0xe0` | 50 | 51 | `0x10000`, `0x1000F`, `0x10010`, `0x10014`, `0x10200`, `0x10500`, `0x10700`, `0x10800`, `0x11800` (= USB grp 0x18) |
| `0x00020000` bsfr | BT / wireless | 5 | 5 | `0x20000`, `0x25800`, `0x27FF8`, `0x2B110`, `0x2EE00` |
| `0x00040000` hsfr | SFC `0x02`, SFC 암호 `0x03` | 3 | 4 | `0x40200`, `0x40204`, `0x40400`, v16만 `0x41200` |
| `0x00050000` psfr | ports | 9 | 9 | `0x50000`, `0x50040`, `0x50044`, `0x501C4`, `0x51000`, `0x5101C`, `0x51020`, `0x51028`, `0x51030` |
| `0x00060000` 대역 | 미분류 | 1 | 1 | `0x60001` |
| `0x01EE0000` csfr | 코어 SFR | 3 | 3 | `0x1EEF100`, `0x1EEF1A0`, `0x1EEF300` (0x01EEF000 서브블록) |
| `0x01F20000` cache | cache-way RAM | 1 | 1 | `0x1F28000` |
| `0x04000000` SDRAM | `ENTRY=0x04000120` | 1 | 1 | `0x4000120` — 부트 코드 `0x0200004A` / `0x02000068`에서 사용, SDK 값과 일치 |

(v15 / v16 열은 서로 다른 즉치 주소의 개수)

등급: **거의 확정**(창 단위 실사용) / **미지**(레지스터 개별 의미, 비트밴드 여부).
`0x1000F`처럼 4바이트 정렬이 아닌 값은 비트밴드/별칭 접근으로 보이나 **추정**이다.

v15와 v16의 차이는 hsfr `0x41200` 1건을 제외하면 **없다.** MMIO 사용은 두 버전이 동일하다.

## §9. 우리가 좁힌 것 (요약)

1. **RAM +0x40 은 부정확.** 실제로는 주소별 `+0x40 / +0x44 / +0x64 / +0x84 / +0x88`. 스냅샷은 `+0x88`.
2. **MMIO 미지 -> 거의 확정.** 창 단위 실사용 주소를 처음 정량화했다.
3. **문자열 풀 위치·크기 확정.** v15 `0x0205D7B5` / v16 `0x0205E1F5`, 양쪽 136개, 추가 6 · 삭제 6.
4. **1.16 신규 데이터 4곳 전부 특정** — 그리고 **참조 코드는 0건**이라는 부정 결과까지.
5. **커버리지 58.2 %** — 우리 맵의 빈 곳이 없는 것이 아님을 수치로 못박았다.
6. **앱 크기 차이의 내역**을 데이터 항목 단위로 분해 (코드 삽입 0 B).

## §10. 비주장

- 이 문서는 **어떤 미지 구간도 자유 공간으로 승격하지 않는다.**
- MMIO 표는 즉치값 기반이며, **개별 레지스터의 의미를 주장하지 않는다.**
- v16의 물리 플래시(파일 오프셋) 대응은 개별 검증되지 않았다.
- RAM 증분 프로파일은 **유일 대응 23쌍의 표본**이며, 경계 주소는 미확정이다.
  `0x01C04414` / `0x01C0491E` (+0x46)는 4의 배수가 아니어서 **주소가 아닐 가능성**이 있다.
- STORAGE 베이스, BSS 소유권, SDRAM 실사용 범위는 확정하지 않았다.
- 016 설치를 권고하지 않는다. v15 기반 복구 자산이 무효화된다.
