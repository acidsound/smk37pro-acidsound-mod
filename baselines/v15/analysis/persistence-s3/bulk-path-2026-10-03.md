## 0. 결론 요약

handoff §5는 "UI → flag table 128 B → 스토리지" 라는 영속 경로를 제시했다.
**주장 중 두 개가 반증되었다.** 그리고 §5가 보지 못한 훨씬 큰 후보 경로의
**코드**를 찾았지만, 그 경로가 실제로 도는지는 확정하지 못했다.

| handoff §5 주장 | 실측 | 판정 |
|---|---|---|
| `FUN_02005512`가 flag 128 B를 쓴다 | **selection 9 B**를 쓴다 (`r2 = #0x9`) | **반증** |
| 그 함수가 UI에서 트리거된다 | 부트 경로 1회 + UI 핸들러 1회 | 부분属实 |
| 128 B면 충분할 가능성 | 9 B면 충분하다(더 작다) | 전제 붕괴 |
| 스토리지는 `+0x9209`에서 닫힌다 | bulk 경로는 `*(g+0x0)` 기준이나 그 필드는 **임시 슬롯** | **미해결 — 진짜 질문이 바뀜** (§3.4a) |

**새 발견:** `FUN_02005fac`에 **151,320 B RAM 창**을 8구간으로
wholesale 저장/복원하는 **코드가 존재한다.** save/load 베이스가 같아 **대칭**이다.

**이 세션이 확정한 것 (P0 전 항목 결속):** `*(g+0x0)`는 **현재 레코드 버퍼
포인터**(`*(g+0x1a8)`)이고, 앱 이미지 안에서 `0x0201d1be`로 초기화된다.
"writer가 없다 → bulk 경로가 죽었다"는 이전 추론은 **기각**됐다.

→ **§3.1의 "151,320 B RAM 창을 wholesale 저장" 해석도 최종 기각.**
   bulk 경로는 고정 오프셋 세트가 아니라 레코드 버퍼 기준 주소로 8회 쓴다.
   (근거: §3.4a · P0-2 · P0-3)

**실기기 동작은 여전히 미확인. 정적 결론만 서술한다.**

## 1. 새 도구

```
tools/smk37_listing_query.py    --range / --func / --xref / --bytes
tools/smk37_callargs.py         스토리지 ABI 호출 지점의 r0/r1/r2 역추적
```

`smk37_callargs.py`는 호출 지점에서 함수 진입점까지 **기호 정방향 실행**해
각 인자를 접는다. verdict는 FIXED / DERIVED / UNKNOWN 3단계이며,
**UNKNOWN은 "증명 실패"일 뿐 "없음"이 아니다** (선형 순회라 UNDER-approx).

69개 호출 지점 전수표가 §3에 있다.

### 1.1 이 도구를 만들면서 겪은 함정 (재발 방지)

Ghidra quarkslab TSV는 아래를 전부 한다. 파서를 지킬 것:

1. **텍스트 컬럼이 mnemonic을 중복 출력** — `mov\tmov r0,#0x1c33260`.
   안 떼면 `mov`이 dst 피연산자로 파싱되어 전부 UNKNOWN이 된다.
2. **dst와 src는 쉼표가 아니라 공백** — `mov r0,#0x1c33260`.
   쉼표 기준으로 `ops[1:]`를 취하면 빈 문자열이 된다.
3. **같은 명령군이 `#` 유무로 두 형태로 출력** —
   `add r0,r0,#0x3a0` 과 `add r1,r1,0x9200`. 정규식单一화가 아니다.
4. **메모리 피연산자가 대괄호 없이** — `ldw r1,r0,#0x160`.
5. 파일 **첫 줄이 헤더**라 `int(fields[0],16)` 이 ValueError.
6. `push rets` 가 함수 프롤로그 표식. 함수 경계 판정에 쓴다.
7. **자기 자신을 클러버하는 call**: 호출 지점까지의 순회에서 call 행을
   포함하면 그 call이 r0-r2를 지워버린다. `b > a` 가 아니라 `b >= a` 로 멈춰야 한다.
8. **store의 base 레지스터는 괄호 안이다.** `sw r0,[r6 + 0x160]` 에서
   base는 `r6` 이지 `r0`(데이터)이 아니다. "마지막 레지스터가 base" 규칙은
   store에서 **항상 틀린다.** → **이 버그가 1판의 "g+0x0에 writer 없음"을 만들었다.**
9. **함수 컬럼은 소문자**다. `FUN_02005512` 가 `fun_02005512` 로 저장되므로
   `"FUN_"+target` 비교는 영원히 실패한다.
10. **call은 volatile만 지운다.** Jieli ABI에서 r4-r11은 callee-saved.
    전부 지우면 "call 뒤의 접근"이 대부분 사라진다(흔한 경우가 예외가 아니다).
11. **`add`로 만든 값은 주소이지 접근이 아니다.** `add r0,r0,#0x3a0` 는
    g-필드 접근으로 기록하면 안 된다. 마찬가지로 `ldw` 결과에 더하는
    `add r1,r1,0x9200` 는 **스토리지 오프셋**이지 g-필드가 아니다.

이 11개 중 **8번이 실제 오판을 유발했고**, 1판 문서의 결론 두 개가 뒤집혔다
(§3.4). **도구 출력을 맹신하지 말고, 알려진 정답을 반드시 통과시킨 뒤에
믿는다.** 이를 자동화한 것이 `--self-test` (양성 5 + 음성 2).

## 2. `FUN_02005512` 정독 (handoff P0 #1)

v15, 전 함수 7줄. 추적기의 판정: **FIXED**.

```
02005512  push rets
02005514  mov  r0,#0x1c33260      ; r0 = g + 0x3a0
0200551a  ldw  r1,r0,#0x160        ; r1 = *(g+0x160)  쓰기 뷰
0200551e  add  r0,r0,#0x3a0
02005522  add  r1,r1,0x9200        ; r1 = 쓰기뷰 + 0x9200
02005526  mov  r2,#0x9              ; len = 9   <<<<<<
02005528  call 0x02004b02           ; write
0200552c  pop pc
```

- **flag 128 B가 아니다. selection 9 B다.**
- handoff §5가 인용한 `+0x9180`(flag 128 B)은 이 함수와 무관하다.
  실제로 flag 128 B를 읽는 곳은 **부트 로더 `0x02005f0e`** 이다
  (`g+0x129c` ← `*(g+0x160)+0x9180`, `r2=#0x80`).
- 9 B를 쓰는 쪽도 대칭으로 부트 로더 `0x02005f20`이다
  (`g+0x3a0` ← `*(g+0x160)+0x9200`, `r2=#0x9`).

즉 `FUN_02005512`는 **selection을 플래시에 올리는 것**이고,
부트 시 `0x02005f20`이 되돌린다. 정상적인 stock round-trip이다.

### 2.1 호출자 2곳

| 호출 지점 | 경로 |
|---|---|
| `0x02005f7c` | `FUN_02005fac` 내부 — bulk 저장 루틴의 selection 덮어쓰기 |
| `0x020295c8` | **UI 핸들러** (handoff §5가 지목한 그 주소) |

UI에서 selection 저장은 실제로 트리거된다. 다만 9 B짜리이고,
우리가 원하는 패드/건반 상태(32 B급)를 담을 공간은 아니다.

## 3. ⭐ 대량 경로 — `FUN_02005fac` (handoff가 놓친 것)

### 3.1 구조 — ⚠️ 아래 "151,320 B 창" 해석은 **P0에서 기각**됨

> 정정: 이 절은 bulk 저장의 **크기/주기**는 정확하나, **목적지 해석이 틀렸다.**
> `*(g+0x0)`는 RAM 창 베이스가 아니라 **레코드 버퍼 포인터**다(P0-3).
> 8회 쓰기는 연속 RAM 창이 아니라 **레코드 버퍼 기준 8구간**이다.
> 아래 수치는 "각 호출의 길이/오프셋"으로만 유효하다.

`FUN_02005fac`는 `0x02005fac` 진입, `r7 = g`로 시작하는 대형 함수다.
중간에 **8연속 write**(`0x020064ba`..`0x02006552`)와
**8연속 read**(`0x0200656c`..`0x020065f2`)가 있다.

각 호출은 `r2 = 0x49e3` (18,915 B) 고정이다.

**소스 오프셋 8개** (리스팅에서 직접 읽음):

```
0x00000  0x049e3  0x093c6  0x0dda9  0x1278c  0x1716f  0x1bb52  0x20535
```

간격이 전부 정확히 `0x49e3` = 연속된 **단일 메모리 윈도**다.
(첫 덩어리의 시작 오프셋 0은 베이스 주소 자체.)

### 3.2 베이스 주소 — 함정

handoff §3.2에 따르면 "S1C 런타임 객체"는 `g = 0x01c33260` 이다.
**이 함수의 소스는 g가 아니다.**

```
02006430  mov r6,r7              <-- r6 = 이전 r7
02006432  mov r7,#0x1c33260      <-- g. r7은 "그 다음" 설정된다
```

`mov r6,r7` 가 `mov r7,#0x1c33260` **보다 앞에 있다.** 그래서 r6은
그 이전 r7이고, 그것은 `0x01c0de20`이다
(함수 내 r7 대입 3곳: `0x02006176`, `0x020061fc`, `0x02006302` 모두
`mov r7,#0x1c0de20`). 마지막이 `0x02006302`이고 `0x02006430` 직전이다.

따라서:

```
bulk RAM 창 = 0x01c0de20 .. 0x01c32d38    span 0x24f18 = 151,320 B
```

### 3.3 스토리지 배치

`r1 = *(g+0x0)` (`_lw r1,[r4+0x0]`, r4=g)에 8개 오프셋을 더한다:

```
+0x00000  +0x05000  +0x0a000  +0x0f000
+0x14000  +0x19000  +0x1e000  +0x23000
```

- 스트라이드 `0x5000` (20 KiB = 스토리지 블록 크기)
- 총 도달 `0x279e3` = **162,275 B (158.5 KiB)**
- 블록당 미사용 여유 `0x5000 - 0x49e3 = 0x61d` = **1,565 B**

### 3.4 ⭐ P0-1 해결 — `*(g+0x0)` 의 정체

> **이 문서 1판은 두 번 틀렸다.** 둘 다 도구 버그였다. 정정 기록이다.

**오정정 1 — store base 레지스터 오인.** `sw r0,[r6 + 0x160]` 에서
base는 `r6`(괄호 안)인데 "마지막 레지스터" 규칙이 `r0`(데이터)을 집었다.
1판은 이 때문에 `g+0x160`의 부트 writer `0x02005eee` 를 **누락**했다.
→ base를 괄호에서 직접 읽도록 수정. `g+0x0` 접근이 23건 → 330건으로 늘었다.

**오정정 2 — 임시 슬롯 패턴 미인식.** base를 고친 뒤에도 `g+0x0`의 32비트
writer가 안 보여 "미초기화" 결론이 남았다. 그런데 **있었다.**

### 3.4a 결정적 증거 — `FUN_02009d1c`

```
02009d32  mov    r4,#0x1c33260      ; r4 = g
02009d38  addldw r0,r4,#0x100         ; r0 = *(g+0x100)
02009d3c  sw     r0,[sp+0x14]        ; *(g+0x100) 를 스택에 백업
02009d3e  add    r0,sp,#0x0          ; r0 = sp (로컬 구조체)
02009d40  sw     r0,[r4 + 0x0]       ; *(g+0x0) = sp   <-- 임시로 빌림
02009d42  call   0x02009c34          ; 무언가
02009d46  lw     r1,[sp+0x14]        ; 백업값 복원
02009d48  sw     r1,[r4 + 0x0]       ; *(g+0x0) = *(g+0x100)  <-- 복원
```

**`*(g+0x0)`는 영구 스토리지 베이스가 아니다.**
`g+0x100` 의 **원래 값을 백업했다가 함수 호출 동안 `sp`로 덮어쓰고 되돌린다.**
전형적인 "전역 슬롯을 임시로 빌려 쓰는" 패턴이다.

따라서:

1. **`*(g+0x0)`는 초기화된다.** 1판의 "쓰는 코드가 없다"는 **기각**.
2. **`FUN_02005fac`가 죽었을 가능성도 기각**된다. 베이스 필드는 정상적으로
   채워진다 (기본값 `*(g+0x100)`, 호출 중에는 `sp`).
3. **다만 bulk 저장 대상이 `sp`일 가능성을 열어야 한다.**
   `FUN_02005fac`의 `_lw r1,[r4+0x0]` 시점에 `*(g+0x0)`가 무엇인지는
   **컨텍스트 의존**이다. 275건의 읽기가 그 값을 계속 바꿔 세운다.
   → **이것이 진짜 남은 질문이다** (§6 P0-2).

### 3.4b 구조 신호 — `g+0x0`는 포인터 필드다

```
g+0x0000   LD 275   ST 16
g+0x0001   LD   0   ST  3
g+0x0002   LD   0   ST  3
g+0x0004   LD   0   ST  9
...  g+0x0001..0x0040  전부 LD 0 / ST 유
```

첫 4바이트만 압도적으로 읽히고 그 뒤 바이트들은 **쓰기 전용**이다.
전형적인 **포인터 + 플래그 바이트簇** 구조다 (little-endian 포인터의
하위 바이트를 개별 플래그로 써먹는 패턴).

→ `g+0x0`를 "스토리지 베이스"라는 §3.3의 가정과 **같은 종류의 필드**로 보는
   것은 위험하다. 실제로는 **다른 무언가**(핸들/임시 슬롯)다.

### 3.4c handoff §3.3과의 관계

§3.3 "스토리지는 +0x9209에서 닫힘"은 `*(g+0x160)` **기준**의 주장이다.
bulk 경로는 `*(g+0x0)` **기준**이다. 필드가 다르면 충돌하지 않는다.

→ **§3.3은 (기저가 다르다는 이 해석 아래에서) 여전히 유효할 가능성이 높다.**
→ 하지만 "닫힘"을 뒷받침하던 근거가 "한 개의 필드를 못 봤다"는 사실로
   약화되었다. **§3.5의 17레코드 예약을 진행하기 전에 §6 P0-1을 끝내야 한다.**

### 3.6 write/read 는 조건분기 하나로 갈린다

```
02006162  add r1,r12,#0x384
02006166  mov r2,#0x8
02006168  mov r0,r5
0200616a  call 0x02048c96          ; 8바이트 비교
02006170  je   r0,#0x0,0x02006558  ; 같으면 READ(복원), 다르면 WRITE
```

매직 8 B 비교 하나로 save/load가 갈린다. 전형적으로
**최초 부팅이면 기본값을 만들어 저장하고, 이후 부팅이면 스토리지에서 복원**하는
구조다. 이 함수가 UI에서 트리거되는지는 §5에 Discuss.

### 3.7 호출 경로

```
FUN_02005fac
  └─ 유일한 호출자: 0x02007008  (FUN_02006762 내부)
       └─ FUN_02006762의 확인된 호출자: 없음 (listing 전수 기준)
```

`FUN_02006762`는 루트다. 바이너리에서 `FUN_02006762`/`FUN_02005fac`의
32비트 포인터는 **0건**이다(직접 call은 1건뿐).
→ **간접 호출(디스패처 테이블) 경로가 listing 커버리지(58.2%) 밖에 있다.**
handoff §8.1의 "콜백 벡터 11 엔트리 dispatcher 미발견"과 **같은 문제**일 가능성이 높다.

## 5. 이 세션이 바꾼 결론

### 5.1 기각

1. **"`FUN_02005512`가 flag 128 B를 영속화한다"** — 기각. selection 9 B.
2. **"스토리지는 +0x9209에서 닫힌다"** — 근거 약화. 같은 베이스에
   0x279e3까지 쓰는 경로가 발견됨. (§3.4 미해결)
3. **"128 B면 충분할 가능성"** — 논거 자체가 성립하지 않음.

### 5.1bis 새로 기각한 것

4. **"`*(g+0x0)`에 쓰는 코드가 없다"** — **기각 (§3.4a).**
   store base 레지스터 오인 버그였다. 실제로는 접근 ~330건.
5. **"대량 경로가 죽었을 가능성"** — **기각 (§3.4a).**
   `FUN_02009d1c`가 이 필드를 정상적으로 백업/덮어쓰기/복원한다.
6. **"151,320 B 대량 경로가 0x01c0de20 창을 그대로 저장한다"** — 여전히 미해결.
   `*(g+0x0)`가 호출 시점에 `sp`일 수도 있다. **P0-2.**

### 5.2 확립 (오프라인 정적 사실)

1. selection 9 B 왕복: `0x02005512`(쓰기) ↔ `0x02005f20`(부트 읽기).
   UI `0x020295c8`이 9 B 저장을 트리거한다.
2. 151,320 B RAM 창의 wholesale 8구간 저장/복원 **코드가 존재하고**,
   write와 read의 베이스가 **같다**(대칭).
   단 저장 베이스 필드 `*(g+0x0)`의 초기화가 미확인이다 (§3.4).
3. 그 창의 S1C5 슬롯은 **포함되지 않는다**.
4. stock SAVE 무력화(§3.4 handoff)는 재확인됨 — v15 기준
   `0x02026da6` = `beeaacee`(raw 0xa3), `0x02026dac` = `bfeac7b9`(packer).
   **v15는 정상이므로** 이건 S1C5 패치의 효과다. v15 리스팅에서는
   stock SAVE가 살아있다.

### 5.3 아직 모르는 것 (비추정) — P0 결속 후 갱신

0. **`*(g+0x0)` (=`*(g+0x1a8)`) 가 가리키는 구조의 정체.**
   8개 독립 섹터에 걸친 저장이라 §3.3의 연속 레코드 blob과는 형태가 다르다.
   이게 §3.3 "닫힘" 주장과 양립하는지 여전히 판단 보류.

- `*(g+0x0)` 과 `*(g+0x160)` 이 같은가 다른가. → §3.3 결론이 이걸 달린다.
- `FUN_02005fac` 가 UI에서 도달 가능한가 (간접 호출 경로 미확정).
- `FUN_02006762` 의 진입점.
- 151,320 B 창의 **어떤 바이트가 실제로 점유돼 있는지.**
  리스팅에서 이 창의 절대주소는 **한 건도 나오지 않는다**(0x01c0de20는
  `mov` 즉시값으로만 등장). 전부 기준포인터+오프셋으로 접근한다 →
  **점유도 분석에 정적 역추적기가 필요하다.**

## 6. 다음 세션 (이 문서가 갱신한 우선순위)

### P0-1 — ✅ 완료 (2회 오정정 포함)

`*(g+0x0)`는 **임시로 빌려 쓰는 전역 슬롯**이다: `FUN_02009d1c`가
`*(g+0x100)`을 백업 → `sp`로 덮어쓰기 → `0x02009c34` 호출 → 복원.
"필드에 writer가 없다 → bulk 경로가 죽었다"는 이전 추론은 **기각**된다.

부수 작업도 끝났다:
- ✅ store base 레지스터 오인 수정 (알려진 정답 `0x02005eee`로 검증)
- ✅ 값 격자(const/g/mem) 도입 — `add rX,rY,rZ` 전파
- ✅ `--self-test` 하네스: 7/7 통과 (음성 케이스 2건 포함)

### P0-2 — ✅ 완료 (질문이 실제로는 더 얕았다)

> "`FUN_02005fac`의 8회 write/read 순간의 `*(g+0x0)` 값은 무엇인가?"

**답: bulk 경로는 `sp` 클러버 경로와 분리되어 있다.** 그래서 `sp` 가 아니다.

**1. `sp`로 덮어쓰는 함수(`FUN_02009d1c`)를 부르는 곳을 전수 확인**

```
FUN_02009d1c 의 직접 호출자: 47건
그 안의 서로 다른 함수: 23개
배치: 전부 0x0200a8xx ~ 0x0200c1xx (UI/MIDI 지대)

FUN_02005fac 의 호출자: 1건 (0x02007008) -> FUN_02006762
FUN_02006762 의 스팬: 0x02006762 .. 0x0200739c (0xc3a)
FUN_02006762 안에 sp-클러버 호출자: 0건
```

→ **교집합이 없다.** bulk 저장 구간에 `*(g+0x0)=sp` 상태로 들어갈 수 없다.

**2. 그래서 남는 후보는 "정상값"인데, 그것의 정체도 바로 알 수 없다**

`g+0x100`은 앱 내에서 **1건만** 접근된다(`0x0200ac46` LD).
`FUN_02009d1c`가 백업하는 그 값조차, 앱 안에서 심어진 게 아니다.

**3. 결론 — `*(g+0x0)`의 초기화는 앱 이미지 안에 없다**

`FUN_02005fac` 진입 시점(`0x02006444`, `r4 = g+0x0`)까지
**32비트 `sw`로 `g+0x0`에 심는 코드가 리스팅에 하나도 없다.**
`g+0x0`의 16개 store를 전수 나열하면:

| 폭 | 개수 | sites |
|---|--:|---|
| `sb` | 9 | `0x02000950`,`0x020013da`,`0x02004f38`,`0x0201df1c`,`0x0202aade`,`0x0202af60`,`0x0202b096`,`0x0202b1b6`,`0x0202b2fe`,`0x0202b31e` |
| `sh` | 3 | `0x02010346`,`0x0201d7da`,`0x02025d2a` |
| `sw` (4B) | 3 | `0x02009d40`,`0x02009d48`(= 임시 슬롯 백업/복원), `0x0201d1be` |

- `sb`/`sh` 12건은 포인터 필드의 하위/상위 바이트를 개별 플래그로 조작하는 것
  (`g+0x0`이 little-endian 32비트 포인터라는 §3.4b 신호와 일치).
- 4B `sw` 중 2건은 임시 슬롯 패턴이고, **1건(`0x0201d1be`)이 남는다.**
  ```
  0201d1b0  addldw r1,r0,#0x1a8
  0201d1be  _sw   r1,[r0 + 0x0]   ; r0 = g + K 일 것이므로 g+K 에 심는다
  ```
  이것도 앱-내 최초 대입일 수 있으나, 도구가 `r0`의 기준을 확정하지 못해
  **후보**로 남는다.

**따라서 (a)/(b) 이분법은 여전히 유효하다** — 다만 (a) 쪽이 강해졌다:

- (a) 로더/부트 ROM이 앱 전에 `*(g+0x0)`를 심는다 → **275개 리더 전부가
  앱 밖 초기화에 의존.** 앱만으로는 이 경로를 재현/검증할 수 없다.
- (b) 앱 내 최초 대입이 `0x0201d1be` 한 곳이다 → 그 경로만 추적하면 된다.

### P0-3 — ✅ 해결. `(a)/(b)` 이분법 종료.

`0x0201d1be` 의 `r0` 기준을 손으로 확정했다:

```
0201d1a6  push   {rets,r15,...}
0201d1a8  mov    r15,#0x1c33260      ; r15 = g
0201d1ae  mov    r0,r15              ; r0 = g
0201d1b0  addldw r1,r0,#0x1a8         ; r1 = *(g+0x1a8)     <== 값
0201d1b4  lw     r2,[r0 + 0x1c]
0201d1ba  mov    r2,#0x3f800000
0201d1be  _sw    r1,[r0 + 0x0]        ; *(g+0x0) = *(g+0x1a8)  <== 최초 대입
```

**`*(g+0x0)`는 앱 이미지 안에서 초기화된다. (a)는 기각.**

그리고 **무엇인지**가 드러난다: `g+0x1a8`은 §3.4 handoff(원문 §3.4)가
**공식 SAVE의 레코드 소스**로 지목한 그 필드다:

```
02026d9e  add r4,r8,0x1a14   ; (원문 §3.4)
02026da6  call 0x02004b02    ; raw 0xa3 레코드 쓰기, r0 = r4 = g+0x1a14
```

→ **`*(g+0x0)`는 `*(g+0x1a8)`(= 공식 SAVE가 쓰는 레코드 소스 필드)에서
복사되는 32비트 포인터**다. 즉 **레코드/데이터 버퍼 계열의 포인터**다.
단, 아래 정정 참조 — 이것만으로 bulk 쓰기 목적지가 레코드 테이블이라고
결론 내릴 수는 없다.

### P0 종합 결론

| 질문 | 답 | 근거 |
|---|---|---|
| `*(g+0x0)`에 writer가 있는가 | **있다** | `0x0201d1be` (`_sw r1,[r0+0]` with `r0=g`) |
| 로더가 심는가 | **아니오** | 앱 내 대입 확인 |
| bulk 저장 시 `sp`인가 | **아니오** | sp-클러버 23개 함수가 bulk 호출 경로와 무교집합 |
| `*(g+0x0)`가 무엇인가 | **레코드 버퍼 포인터** (`*(g+0x1a8)`) | `0x0201d1b0/1be` |

**§3.1의 "151,320 B 연속 RAM 창 저장" 해석은 기각한다.**
`0x02006444` 의 `r1 = *(g+0x0)` 는 런타임 포인터(버퍼)라 고정 오프셋 세트가
아니다. 다만 **정적으로 확정하지 못한 것**이 남는다:

- 8개 스토리지 오프셋은 `0x0, 0x5000, ... 0x23000` = **8개 독립 섹터**
  (각 0x5000)에 걸쳐 있다 → **하나의 연속 blob이 아니라 8개 영역**이다.
- 길이 `0x49e3`은 §3.3의 레코드 단위 `0xa3`의 배수가 **아니다**
  (`0x49e3 / 0xa3 = 116.04`). → **레코드 테이블 전체가 아니다.**

→ 즉 "레코드 버퍼를 스테이징으로 8개 섹터에 분산 저장/복원"인지,
  아니면 `*(g+0x0)`가 가리키는 대상 자체가 (§3.3의 record blob이 아닌)
  별개 구조인지 **미결**이다. **동작을 주장하지 않는다.**

> **이 결론은 손독 + 도구 2독(정적)으로 지지된다. 실기기 동작은 미확인.**
> 남은 검증은 (1) `*(g+0x0)` 값이 bulk 8회 호출 중 변하지 않는지,
> (2) `0x49e3` 크기가 레코드 영역 전체와 맞는지 — 둘 다 **정적**으로 가능하다.

## 8. 비주장

- **대량 경로가 실기기에서 동작한다고 주장하지 않는다.** 정적 리스팅 근거뿐이다.
- **151,320 B 창의 미점유 영역이 존재한다고 주장하지 않는다.** 아직 증명 없다.
- **`FUN_02005fac` 가 UI 트리거 경로라고 주장하지 않는다.** 호출자가 1건이고
  그 상위가 루트다.
- **§3.3이 틀렸다고 확정하지 않는다.** 기저가 다를 수 있고, 그것이 미해결이다.
- **대량 경로가 동작한다고 주장하지 않는다.** `*(g+0x0)`가 그 시점에
  무엇인지(§3.4a의 임시 슬롯 vs `*(g+0x100)`) 미확정이다.
- **bulk 저장이 0x01c0de20 창을 대상으로 한다고 확정하지 않는다.** P0-2.
- **`g+0x0`이 스토리지 베이스라는 주장을 확정하지 않는다.** 임시 슬롯이다.
- **`tools/smk37_g_fields.py` 출력을 정답으로 취급하지 않는다.**
  store base 오인은 고쳤고 `--self-test` 7/7(음성 2건 포함)이 통과하지만,
  **pre/post-index store(`sb r6,[++r0=r4]`)는 여전히 오탐을 낸다.**
  `g+0x0`의 ST 16건 중 몇 건은 그럴 수 있다.
- v15 리스팅 기준으로 S1C5 패치 효과는 직접 관찰하지 않았다 (§5.2 #4은
  v15 바이트 값의 재확인이다).
